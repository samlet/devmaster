# 05 指标与报表口径

> 更新：2026-10-28 · 对应 M6
>
> 报表只回答"团队怎么流动"，不回答"谁干得多"。所有指标都从
> `work_items` + `work_item_events` 推导，不引入第二套事实。

## 1. 共同前提

- **时间一律 UTC**，展示时再转本地时区。
- **完成** = 首次进入 `DONE / CLOSED / VERIFIED / WONTFIX` 的迁移；
  `CANCELLED` 不算完成（它从 scope 移除，不是交付）。
- **在研** = `IN_PROGRESS / IN_REVIEW`（含 BUG 的 `RESOLVED`）。
- **未完成** = 除上述完成态与 `CANCELLED` 之外的所有状态。
- 重开（`REOPENED`）不撤销"完成"事实：一个工作项只计一次完成，取**首次**完成时间。
  重开后的再次完成不会让吞吐翻倍。

## 2. 周期时间（Cycle Time）

```text
cycle_time = 首次完成时间 − created_at
```

- 只统计**统计窗口内完成**的工作项（按完成时间过滤，不按创建时间）。
- 按 `type` 分组；样本 < 5 时不输出分位数（避免"1 个样本的 P95"）。
- 分位数用 nearest-rank：排序后取 `ceil(p × n) − 1`。
- 输出 P50 / P85 / P95（小时）。

**与 02 §3.8 的差异**：那里写的是 `resolved_at − created_at`，只对 BUG 成立
（`resolved_at` 在 RESOLVED 时写）。M6 统一改成"首次完成迁移"，否则 STORY/TASK
的周期时间永远是空。

## 3. 吞吐（Throughput）

```text
吞吐 = 每周首次完成的工作项数，按 type 分组
```

- **不看点数**：点数会被"估大"污染，完成数不会。
- 周以周一为起点（`date_trunc('week')`）。
- 同一工作项只计一次（首次完成）。

## 4. 累积流图（CFD）

- 每日各**看板列**的存量：待办（TODO/OPEN/REOPENED）、进行中（IN_PROGRESS）、
  评审中（IN_REVIEW/RESOLVED）、完成（DONE/VERIFIED/CLOSED/WONTFIX）。
- 由事件折叠得到：先取窗口开始时的存量（每项最后一条早于窗口的 `to_status`），
  再按天应用窗口内的事件。
- `BACKLOG` 与 `CANCELLED` 不进图（它们不在看板上）。

## 5. 团队负载（Team Load）

按 `assignee_id` 分组（未指派单列）：

- **未完成数**：该人当前未完成的工作项数；
- **在研数**：`IN_PROGRESS / IN_REVIEW / RESOLVED`；
- **未完成点数**：未完成项的 `story_points` 之和（未估点按 0）。

这是**负载**，不是绩效：它只说明"手上压了多少"，不说明"产出多少"。
两个指标必须分开放，否则会诱导把负载当成考核。

## 6. 性能基线

- 目标：10 万工作项下，报表接口 **P95 < 300ms**。
- 测法：`make perf-baseline`（默认 10 万项、20 次请求），分别打
  `/api/reports/cycle-time`、`/api/reports/team-load`。
- 环境：本地 PostgreSQL 18、单进程 server；只作为回归基线，不是容量承诺。

## 7. 不做的指标

| 不做 | 理由 |
|---|---|
| 个人产出排名 | 负载 ≠ 绩效；排名会诱导刷小项、拆项 |
| 故事点速度（velocity） | 点数跨团队不可比；吞吐用完成数 |
| 代码行数 / 提交数 | 与交付价值无关，且可被轻易操纵 |
| 缺陷密度（按 KLOC） | 没有可靠的代码量口径 |
