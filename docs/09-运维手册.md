# 09 运维手册

> 更新：2026-10-28 · 对应 M0–M6
>
> 这份手册回答三件事：**什么时候跑哪个命令**、**跑失败了看哪里**、**哪些操作不可逆**。
> 设计与裁决不在这里，见 01/03/04/06。

## 1. 拓扑与端口

| 组件 | 地址 | 说明 |
|---|---|---|
| `server` | gRPC `:50091` / HTTP `:8291` | 业务读写、`/healthz`、`/metrics`、只读 `/api/*` |
| `web` | `:3031` | Next.js 控制台（只读） |
| `relay` | 无 | outbox → JetStream，常驻 |
| `worker` | 无 | Temporal worker（Ping + ReleaseWorkflow） |
| `consumer` | 无 | 消费 `release.submitted` 起发布工作流 |
| PostgreSQL | `:5432` | `devmaster_dev` / `devmaster_test` |
| NATS | `:4222` | 流 `DEVMASTER_EVENTS`（`dev.>`） |
| Temporal | `:7233` | namespace `devmaster` |
| approver | `:18090`（HEADER 模式） | 发布审批 |
| Gitea | `:3123` | 提交 / tag / webhook |
| artifact content-api | gRPC `:50071` / probe `:18085` | 证据存证（发布链 `SealEvidence`） |
| Keycloak（artifact realm） | `:18280` | `content-worker` 的 client_credentials 令牌 |

## 2. 启动与停止

```bash
make db-create && make migrate   # 首次
make dev                          # server + relay + worker + consumer
make web-dev                      # 控制台
```

`make dev` 的约定是**同起同停**：任一进程退出，整组退出。不要只重启其中一个而让其余继续跑——
relay 停了 outbox 会积压，worker 停了发布会卡在 PENDING_APPROVAL，consumer 停了 E9 不会被消费。

## 3. 定时任务

| 任务 | 频率 | 命令 | 失败后果 |
|---|---|---|---|
| 报表日快照 | 每日 01:00 | `make report-snapshot DAYS=1` | CFD/吞吐回退实时计算（慢但正确） |
| 冲刺燃尽快照 | 每日 01:10 | `make snapshot` | 燃尽图缺点，不影响事实 |
| Gitea 对账 | 每日 02:00 | `make gitea-reconcile` | 漏 webhook 的提交关联缺失 |
| 事件折叠对账 | 每周一 03:00 | `make reconcile` | 当前态与事件日志漂移未被发现 |
| outbox 投递 | 常驻 | `make relay` | 事件积压，PPM/it-solution 收不到 |

所有定时任务都幂等，可以安全重跑；`report-snapshot` 同一天重跑是覆盖。

## 4. 健康检查

```bash
curl -s localhost:8291/healthz   # 200 ok / 503 degraded，components 指出哪个依赖挂了
curl -s localhost:8291/metrics | grep '^devmaster_'
```

关键指标：

- `devmaster_outbox_pending`：持续 > 0 说明 relay 没跑或 NATS 不可达；
- `devmaster_outbox_failed_total`：增长说明投递在重试；
- `devmaster_products_created_total`：只作业务量参考。

## 5. 故障处理

| 现象 | 先看 | 处理 |
|---|---|---|
| `/healthz` 503，`postgres` down | `pg_isready` | 起 PG；连接池会自愈，无需重启 server |
| `nats` down | `nats server check` | 起 NATS；relay 会重连，outbox 不丢 |
| `temporal` down | `temporal operator namespace list` | 起 Temporal；已启动的工作流恢复后继续 |
| outbox 积压 | `SELECT count(*) FROM outbox_events WHERE sent_at IS NULL` | 先确认 relay 进程；再看 `last_error` |
| 发布卡在 `PENDING_APPROVAL` | `GetRelease` 的 `approval_instance_id` | 到 approver 看实例；审批超时后工作流会置 FAILED，可新建一次发布 |
| webhook 401 | Gitea hook 的 secret 与 `gitea.webhook_secret` | 改一致；Gitea 会重投，delivery 幂等 |
| 提交没关联 | `SELECT * FROM inbox_events WHERE source_system='gitea'` | 没有记录→webhook 没到；有记录但没关联→key 不在产品集合 |
| PPM 投影失败 | PPM 的 `inbox_events` 与 `last_error` | 缺费率会 DEFERRED（不是丢），补费率后自动重放 |
| 工时记错 | `GetWorkLog` | **不要改原记录**，用 `ReverseWorkLog` 负向更正 |

### 5.1 发布失败后的重试

发布记录是**一次尝试**：FAILED 后不要改它的状态，重新 `SubmitRelease` 会新建一条。
版本范围在第一次提交时已冻结（`scope_frozen_at`），这是刻意的——重试不能偷偷换范围。

### 5.2 事件对账不一致

`make reconcile` 非零退出时，先看输出里的 `MISMATCH` 行：

```bash
make reconcile ORGANIZATION_ID=<uuid>
```

当前态与事件日志不一致通常意味着有人绕过 `Transition` 直接改库。先冻结相关产品的写入，
导出该工作项的 `ListWorkItemEvents` 与当前行，再决定以哪边为准；不要直接改 `status` 抹平差异。

## 6. 数据维护

### 6.1 迁移

```bash
make migrate-status      # 当前版本
make migrate             # 应用到 devmaster_dev
make migrate-test        # 应用到 devmaster_test
```

迁移只前进。回滚需要手写 down SQL，本仓不提供自动回滚——生产回滚应走备份恢复。

### 6.2 备份与恢复

```bash
pg_dump -Fc devmaster_dev > devmaster_$(date +%F).dump
pg_restore -d devmaster_dev --clean --if-exists devmaster_$(date +%F).dump
```

`work_item_events` / `work_logs` 是 append-only，恢复后仍需保证触发器存在（迁移会建）。

### 6.3 清理

| 对象 | 命令 | 注意 |
|---|---|---|
| 过期幂等键 | `DELETE FROM idempotency_keys WHERE expires_at < now()` | 可安全删除 |
| 已发送 outbox | `DELETE FROM outbox_events WHERE sent_at < now() - interval '7 days'` | 建议先归档 |
| 性能基线数据 | `perfbaseline` 默认自动清理 | 清理会临时关闭事件触发器，失败时务必确认触发器已恢复 |

### 6.4 性能基线

```bash
make perf-baseline                 # 10 万项，需 server 在跑
```

报表走日快照；如果基线突然变慢，先确认 `report-snapshot` 有没有跑，再看 `EXPLAIN`。

## 6.3 控制台登录

控制台用 Keycloak 登录（Authorization Code + PKCE），登录后：

- 提交发布时 `submitted_by` 记的是**你**的 Keycloak `sub`，不是固定值；
- 收件箱自动把 `user:<anchor>` 并进来（用 `sub` 解析主体锚点）。

```bash
./scripts/keycloak-dev.sh start   # :18281，导入 realm-devmaster.json（dev-mem，重启即重置）
./scripts/keycloak-dev.sh info    # issuer 与测试账号
```

| 环境变量 | 作用 |
|---|---|
| `DEVMASTER_OIDC_ISSUER` | 默认 `http://127.0.0.1:18281/realms/devmaster` |
| `DEVMASTER_OIDC_CLIENT_ID` | 默认 `devmaster-web` |
| `DEVMASTER_OIDC_REDIRECT_URI` | 默认 `http://127.0.0.1:3031/api/auth/callback` |
| `DEVMASTER_SESSION_SECRET` | **必填**，≥32 字符，用于加密会话 cookie |
| `DEVMASTER_AUTH_MODE` | `oidc`（默认）/ `dev`（跳过 IdP，直接以指定主体登录，仅本地） |

| 现象 | 先看什么 |
|---|---|
| 登录后回跳 `/login?error=Invalid scopes` | realm 的 client 缺少 `profile`/`email` scope；内置 scope 在导入时尚未创建，必须显式定义 |
| 登录后回跳 `/login?error=state 不匹配` | cookie 被清或跨端口访问；state 一次性，重新点登录即可 |
| 收件箱显示「主体目录里没有该身份的映射」 | 该 `sub` 还没在 subject-registry 里 `Bind("keycloak", sub)`；这是正常降级 |
| `DEVMASTER_SESSION_SECRET` 未设置 | 页面报错；它是必填项，不提供默认值（默认值等于把会话密钥写进仓库）。`make web-env` 会生成一份 |
| `next dev` 启动即退出，报 `safe-delete` / `.next` 删除失败 | 环境注入了 `NODE_OPTIONS`（某些沙箱/安全 shim）。用 `env -u NODE_OPTIONS make web-dev` |

会话只存 `sub/name/email/roles/exp`，**不存 access token**：控制台的读走服务端直连、
写走 BFF 签名，都不需要把用户令牌带在浏览器里。

## 6.35 控制台写通道

控制台有四个写操作：**新建工作项**、**编辑工作项**、**状态流转**、**提交发布**。
它们不走 gRPC——浏览器不能直接调，而 Next 服务端已经在用 HTTP 面。链路是：

```text
浏览器表单 → Next route handler → 签名 → POST /api/work-items
                                        PATCH /api/work-items/{id}
                                        POST /api/work-items/{id}/transition
                                        POST /api/releases
```

编辑工作项时会按顺序发两次写：先 `Update`（标题/优先级/描述），再 `Assign`（经办人）。
第二次用第一次返回的新版本——两次都必须过 CAS，所以「改标题并指派」不会互相覆盖。

签名是 HMAC-SHA256 over `timestamp + "\n" + body`，密钥 `integrations.bff_shared_secret`
只存在于服务端。用户身份由 Next 服务端填（`DEVMASTER_CONSOLE_SUBJECT`，本地默认
`local-dev`），客户端传什么都覆盖不了——否则任何人都能冒充别人提交发布。

| 现象 | 先看什么 |
|---|---|
| 提交后提示「未配置 DEVMASTER_BFF_SECRET」 | Next 进程没读到密钥；后端配置里的 `integrations.bff_shared_secret` 必须与它一致 |
| 提示 `invalid bff signature` | 两边密钥不一致，或系统时钟偏差超过 5 分钟 |
| 提示 `FAILED_PRECONDITION: version scope is frozen` | 该版本已提交过一次发布；失败后重试要新建 ReleaseRecord（这是设计，不是 bug） |
| 直打后端 401 | 预期：两个写端点都只接受带签名的请求，密钥未配置时一律拒绝 |
| 流转提示 `assign the work item before starting it` | 进入「进行中」前必须先有经办人（领域守卫，不是 bug） |
| 流转提示 `only DEV_LEAD can cancel` | 取消是管理动作；需要 `DEV_LEAD` 角色 |
| 流转提示 `cancel requires a reason in comment` | 取消必须填备注 |
| 流转提示 `work item was modified by someone else` | 版本冲突：别人先改了，刷新页面再操作 |
| 流转按钮显示「—」 | 当前状态是终态（DONE/CLOSED/CANCELLED），没有可流转目标 |
| 编辑提示「缺少工作项版本」 | `expected_version` 缺失。注意**新建的工作项版本就是 0**，0 是合法值，只有「没传」才算缺 |
| 新建后列表里没有 | 检查 `return_to` 是否带筛选条件（比如 status=BACKLOG 而新项是 BACKLOG 应能看到）；搜索 `q` 只匹配标题不匹配 key |

写端点**没有**「没配密钥就放行」的降级——那是把一次配置遗漏变成永久后门。

## 6.4 待审批催办

审批等待超过 `notify.approval_reminder_after`（默认 1h，环境变量
`DEVMASTER_NOTIFY_APPROVAL_REMINDER_AFTER`）时发一次 `release.approval_pending`
提醒，只发一次——反复催办会让审批人对整个通道脱敏。

- 阈值不小于 `approver.poll_timeout` 时会被压到一半（否则到点先超时，提醒永远发不出来）；
- 催办是旁路：发送失败只记日志，不影响审批轮询；
- 超时仍走 `release.failed`，原因里带已等待时长（如 `approval timed out after 2h30m0s`），
  不额外发第二条通知。

模板在 notify 仓 `migrations/0005_seed_devmaster_approval.sql`。

## 6.45 主体目录与通知定向

`subject_registry.enabled=true` 时，发布成功/失败通知会先解析提交人：
`Resolve("keycloak", SubmittedBy)` 命中就发给 `user:<anchor_id>`，否则落到团队收件箱。

| 现象 | 先看什么 |
|---|---|
| 通知仍在团队箱 | 该提交人没在 registry 里 `Bind("keycloak", sub)`；这是正常降级 |
| `subject resolve failed` | subjectd 是否在 `:50095`；`DEVMASTER_SUBJECT_REGISTRY_TOKEN` 是否与服务端一致 |
| 催办只发到 `role:RELEASE_APPROVER` | 三种可能：① 该实例当前没有待办；② 待办人没在主体目录登记（`Resolve("approver", id)` 与 `Resolve("keycloak", id)` 都未命中）；③ approver 端点调用失败——看 worker 日志 `query pending assignees failed` |

手工核对与登记：

```bash
subjectctl resolve -source keycloak -external <sub>   # 未命中退出码 3
subjectctl bind -source keycloak -external <sub> -kind PERSON -name "张三" -method OIDC_SUB
```

## 6.5 artifact 证据存证

发布链最后三步是「打 tag → 存证 → 置 PUBLISHED」。存证失败发布会停住，
不会产出「发布了但没证据」的记录。排障顺序：

| 现象 | 先看什么 |
|---|---|
| `obtain artifact access token` | Keycloak `:18280` 是否在跑；`content-worker` 的 secret 与 `configs/local.yaml` 是否一致 |
| `active content type not found` | 该租户没跑 `registry-seed -profile devmaster` |
| `upload does not satisfy content type policy` | 资源角色不是 `evidence`，或载荷超 64 KiB |
| `evidence read-back mismatch` | 写入的字节被改过；这是**失败**，不要重试掩盖，先查 artifact 侧审计 |
| `revision is not working` 且确认密封态成立 | 正常：重试时修订已密封，客户端会当作成功 |

自检与验收：

```bash
make evidence-check    # 写一份证据并回读，打印 ref / sha256
make test-evidence     # 首封新建 + 重放命中同一修订 + 载荷变化落新修订
```

`artifact.enabled=false` 是本地无 artifact 时的显式降级（`evidence_ref` 退化为
发布说明引用）；生产环境 `Validate` 会直接拒绝启动。

## 7. 安全

- **生产 `auth.enabled=false` 启动即失败**，这是配置校验，不是建议。
- Gitea token 只放 `backend/configs/local.yaml`（已 gitignore）；仓库里只有空值。
- webhook secret 与 Gitea hook 必须一致，失败返回 401。
- 运行时角色 `devmaster_app` 非 owner，受 RLS 约束；迁移用 `devmaster_owner`。
- 事件与工时不可改：触发器会拒绝 `UPDATE/DELETE`，需要更正时用业务接口。
- artifact 的 `content-worker` secret 与 Gitea token 同级别：只放 `local.yaml`，
  生产走密钥管理；它只有 `content.service` 一个角色，不能读别人的内容。
