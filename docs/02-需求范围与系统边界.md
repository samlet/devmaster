# 02 需求范围与系统边界

> 上游：[01 方案评估与关键决策](01-方案评估与关键决策.md)（D1～D4 已确认）。
> 本文回答"做什么、不做什么、谁拥有哪个事实、谁有什么权限"。
> 领域模型与表结构见 [04](04-领域模型与数据设计.md)，接口与事件见 [06](06-集成契约与事件设计.md)。

## 1. 一句话定位

**devmaster 是软件研发的执行事实源。** 它回答四个问题：

1. 谁在改什么、为什么改、改到哪一步（工作项与状态迁移）；
2. 这一轮迭代承诺了什么、中途加了多少（冲刺与范围变更）；
3. 这版软件包含哪些改动、什么时候发的、谁批的（版本与发布记录）；
4. 这些改动花了多少人工（工时）。

它不回答：这个项目花多少钱（PPM）、这笔账怎么记（FI）、这版部署到哪些客户（it-solution）、
线上出了什么事故（it-swarm）。

## 3. v1 范围

### 3.1 产品与组件

- **Product**：`key`（2–10 位大写字母数字，如 `HOSP`）、名称、描述、状态（`ACTIVE` / `ARCHIVED`）。
  一个 Product 对应一个被开发的软件；`key` 决定工作项编号前缀。
- **Component**：产品内的模块树（可空层级），带负责人。缺陷必须选组件（守卫可配），
  用于"这个模块最近坏得多不多"。
- **成员**：`product_members(product_id, user_id, role)`，角色见 §6。
- **字段注册表**：`field_registry` 声明该产品允许的自定义字段（键、类型、是否必填、适用类型）。
  这是 D3 的落点：字段可扩展，工作流不可配置。

### 3.2 工作项

| 类型 | 用途 | 可进冲刺 | 可估点 | 特有字段 |
|---|---|---|---|---|
| `EPIC` | 跨迭代的大颗粒目标 | ❌ | ❌ | 无 |
| `STORY` | 用户价值单元 | ✅ | ✅ | 验收标准 |
| `TASK` | 工程任务 | ✅ | ✅ | 无 |
| `BUG` | 缺陷 | ✅ | ✅ | severity / environment / affects_version / 复现步骤 / 期望与实际 |
| `SUBTASK` | 父项拆分 | ❌（跟随父项） | ❌ | 无 |

**公共字段**：编号、标题、描述（Markdown）、状态、优先级（`P0`–`P3`）、经办人、报告人、
产品、组件、标签、冲刺、修复版本、父项、链接、附件、关注人、截止日、估点、预估分钟、
剩余分钟、排序、`project_code` / `wbs_code`、`external_ref`、自定义字段、CAS 版本号。

**操作**：创建、编辑、状态迁移、指派、批量迁移/指派/加版本、复制、关注、评论（Markdown）、
附件（artifact 引用）、链接（`BLOCKS` / `BLOCKED_BY` / `RELATES` / `DUPLICATES` / `CAUSES`）、
搜索（全文 + 结构化过滤 + 保存视图）。

**明确不做**：子任务再拆子任务（只一层）、跨产品移动（复制代替）、工作项模板市场。

### 3.3 看板与冲刺

- **Board** 绑定一个 Product，可选按 Component 过滤；列固定四列（待办 / 进行中 / 评审中 / 完成），
  按状态类别映射（BUG 的 `OPEN`/`RESOLVED` 也落在对应列，映射表见 [04 §3.2](04-领域模型与数据设计.md)），
  `BACKLOG` 不进看板。
- **拖拽**：改状态 + 改排序，一次请求完成（避免两次写导致中间态）。
- **WIP 提示**：某列超过阈值只提示，不阻断（阻断会让人绕过系统）。
- **Sprint**：`PLANNED → ACTIVE → CLOSED`；一个 Board 同时最多一个 `ACTIVE`。
- **入板**：工作项加入 sprint 时，同事务把 `BACKLOG` 提升为 `TODO`——不存在"在板上但还是 backlog"的状态。
- **承诺**：`start` 时批量提交 scope，写 `COMMITTED` 事实；`ACTIVE` 期间增删写 `ADDED` / `REMOVED`；
  完成写 `COMPLETED`（由状态迁移派生，不单独提交）。
- **关闭**：未完成项显式选择"回流 backlog"或"迁入下一 sprint"，不自动。
- **燃尽**：按天快照 + 范围变更重算，两条线（理想 / 实际）分开画。

### 3.4 缺陷

- `severity`：`BLOCKER` / `CRITICAL` / `MAJOR` / `MINOR` / `TRIVIAL`。
- `environment`：`DEV` / `STAGING` / `PROD` + 平台（`WIN` / `MAC` / `IOS` / `ANDROID` / `SERVER`）。
- `affects_version`：受影响版本（链 A 的起点）；`version`（修复版本）在 `RESOLVED` 时必填（守卫可配）。
- **修复时限**：按 severity 配置内部计时器（如 `BLOCKER` 24h、`CRITICAL` 72h），
  超时通知经办人与 lead。**这是内部节奏，不是客户 SLA**（客户 SLA 在 it-swarm）。
- **复现**：复现步骤（Markdown）、期望/实际、构建号、附件（日志/截图/录像，走 artifact）。
- **关闭**：`CLOSED` 必须带 resolution；`REOPENED` 保留历史次数（用于"反复修的 bug"统计）。

### 3.5 版本与发布

- **Version**：`product + name`（如 `2.4.1`）唯一；状态 `PLANNED → IN_PROGRESS → RELEASED → ARCHIVED`
  （+ `CANCELLED`）；`milestone_label` 用于 Alpha/Beta/Gold 这类外部里程碑分组。
- **Scope**：工作项通过 `version_id` 归属；`RELEASED` 后 scope 冻结（只能开新版本）。
- **ReleaseRecord**：一次发布尝试，`PENDING_APPROVAL → APPROVED → TAGGED → PUBLISHED`（+ `FAILED`）；
  带 `tag`、`commit_from` / `commit_to`、审批实例 ID、证据引用、发布人/时间。
- **发布说明**：Markdown 存 artifact（固定版本），正文只存 `content_id:revision_id`。
- **发布审批**：走 approver 的 `devmaster-release-approval` 流程（可配置为必须）；
  审批通过才允许打 tag 与发布。
- **不做**：部署编排、灰度、回滚执行。部署是 it-solution 的事实。

### 3.6 工时

- `minutes`（正整数）、`work_date`、备注、`project_code` / `wbs_code`（默认继承工作项，可覆盖）。
- **只增不改**：更正走反向记录（`reversal_of`），两条都保留。
- **归集**：工时挂在工作项上；工作项带项目/WBS 时自动继承，允许单条覆盖（如跨项目支援）。
- **不做的**：计时器（v1 手工填）、审批工时、加班系数、费率。费率在 PPM。

### 3.7 代码关联

- Gitea org webhook（push / pull_request / tag）→ 解析 commit message 中的工作项编号
  （`\b[A-Z][A-Z0-9]{1,9}-\d+\b`）→ `work_item_commits`。
- PR 状态（`OPEN` / `MERGED` / `CLOSED`）回写到关联记录；`IN_REVIEW` 守卫可要求"至少一个 merged PR"。
- **每日对账**：按 repo + since 拉 Gitea API 补齐丢失的提交（webhook 不可靠，见 01 §6.3）。
- **不做**：代码托管、代码评审、CI 触发、分支策略。

### 3.8 报表（M6）

| 报表 | 口径 |
|---|---|
| 周期时间 | `resolved_at - created_at`，按类型/产品/severity 分组，取 P50/P85 |
| 吞吐 | 每周完成数（按类型），不看点数（点数会被"估大"污染） |
| 累积流图 | 每日各状态存量，由事件折叠 |
| 范围蔓延 | `added_after_start_points / committed_points` |
| 缺陷逃逸 | `environment=PROD` 的缺陷 / 全部缺陷（按版本） |
| 版本采纳 | 版本 → 部署客户数（数据在 it-solution，见 06 §6） |

## 4. 明确不做（v1）

| 不做项 | 理由 |
|---|---|
| 可配置工作流 / 字段配置方案 / 权限方案 | D3；复杂度换不来收益 |
| JQL、自动化规则引擎、插件市场 | 半个产品，调试成本极高 |
| 软件测试用例与执行 | 01 O4；与 QA 仓（物料 IQC）无关 |
| 美术/音频资产生产跟踪 | 01 O3；需要 DCC/Perforce 集成 |
| 客户报障、值班、客户 SLA | it-swarm（Incident）/ it-solution（ServiceTicket） |
| 部署、灰度、回滚 | it-solution |
| 财务核算、成本分摊、费率 | FI / PPM |
| 代码托管、CI/CD、制品库 | Gitea / 外部 CI |
| 即时通讯、视频、白板 | 不做协作套件 |
| 移动端 App | v1 只做响应式 Web |
| 多语言界面 | v1 中文；文案集中管理，为将来留口 |

### 5.1 四条容易搞错的边界

**① devmaster 的 `Product` ≠ PPM 的 `Project` ≠ engagement 的 `Project`**

- devmaster `Product`：被开发的软件（`hospitality` / `fi` / `ppm`），生命周期以年计。
- PPM `Project`：一次交付责任与成本的容器（某客户的酒店项目），有起止、有预算。
- engagement `Project`：用工履约容器，已被 PPM 裁决为"独立结点，无耦合"。

三者之间只有一条弱引用：工作项上的 `project_code`（可空）。**一个 Product 可以服务多个 Project
（一个软件卖给十个客户），一个 Project 也可能用多个 Product（解决方案组合）**，所以不能合并。

**② devmaster 的 `Version` ≠ PLM 的 `Release`**

PLM 的 Release 是工程快照（Rev A/B、BOM、ECO），面向制造；devmaster 的 Version 是软件交付版本，
面向部署。二者不互相同步（01 ADR-0005）。it-solution 的 `Deployment` 只认软件版本。

**③ devmaster 的 `BUG` ≠ it-swarm 的 `Incident`**

- BUG：代码缺陷，有复现步骤、影响版本、修复版本，生命周期终止于 `CLOSED`。
- Incident：服务中断，有影响范围、恢复时间、SLA，生命周期终止于"服务恢复"。

一个线上故障可能由多个 BUG 引起，一个 BUG 也可能引发多个 Incident。**只做引用，不复制状态机**：
BUG 上记 `external_ref`（Incident 号），Incident 上记修复版本，两边各自推进。

**④ devmaster 的 `WorkLog` ≠ workforce 的报工**

- devmaster：研发工时，粒度是**工作项**，用于项目人工成本归集（链 B）。
- workforce：制造/运营工时，粒度是**班次/工序**，用于产线人工成本与考勤。

两者都进 PPM 的 `LABOR`，但来源不同（`source=DEVMASTER` / `source=WORKFORCE`），
PPM 按来源分别对账，不合并成一条"总工时"。

## 6. 角色与权限

| 角色 | 范围 | 权限 |
|---|---|---|
| `DEV_VIEWER` | 组织 | 只读所有产品的工作项、看板、版本、报表 |
| `DEV_MEMBER` | 产品成员 | 建/改工作项、评论、记自己的工时、拖自己负责的卡片 |
| `DEV_LEAD` | 产品成员 | 管 sprint（开始/关闭/范围变更）、指派他人、关闭他人工作项、管版本 |
| `RELEASE_APPROVER` | 组织 | 审批发布（approver 侧角色，devmaster 只读结果） |
| `DEV_ADMIN` | 组织 | 产品/组件/字段注册表/成员/组织映射 |

**规则**：

1. 组织隔离在数据库层（RLS），产品可见性在应用层（`product_members`）。
2. 跨产品读：`DEV_VIEWER` 可读全组织；普通成员只能读自己所在产品 + 被显式授权的产品。
3. 关闭他人工作项需要 `DEV_LEAD`；`BUG` 的 `VERIFIED` 只能由报告人或 `DEV_LEAD` 执行
   （防止"自己修自己验"）。
4. 发布审批人与发布执行人**不能是同一人**（四眼，approver 侧强制）。
5. 服务身份（`devmaster-service`）只能调用集成专用 RPC（`CheckVersion`、`IngestGitea` 等），
   不能调用业务写接口。

## 7. 术语表

| 术语 | 定义 | 易混淆点 |
|---|---|---|
| Product | 被开发的软件，有稳定 key | 不是项目、不是客户、不是解决方案 |
| Component | 产品内的模块树节点 | 不是微服务（一个组件可能跨多个服务） |
| WorkItem | 工作项，五类类型的统称 | 不是"任务"的同义词；TASK 只是其中一类 |
| Board | 看板，绑定 Product | 不是 Sprint；一个 Board 有多个 Sprint |
| Sprint | 时间盒 + 承诺快照 | 不是"里程碑"；里程碑用 Version.milestone_label |
| Version | 软件交付版本 | 不是 PLM 的 Release；不是 Git tag（tag 是 ReleaseRecord 的字段） |
| ReleaseRecord | 一次发布尝试 | 一个 Version 理论上可有多次尝试（失败重试） |
| WorkLog | 一条工时记录 | 不可编辑；更正走反向记录 |
| Resolution | 关闭原因 | 不是状态；`CLOSED` 必须带 resolution |

## 8. 非功能需求

| 维度 | 要求 |
|---|---|
| 规模 | 10 万工作项 / 100 万事件 / 50 并发用户 / 写峰值 10 rps |
| 查询 | 看板与列表 P95 < 300ms；全文检索 P95 < 500ms |
| 一致性 | 单库事务；跨系统最终一致（outbox + 幂等消费） |
| 可用性 | 单实例，无 HA；RTO 由备份恢复决定（与 PPM 同），不做多活 |
| 审计 | 状态迁移永久保留；字段编辑保留 180 天（压缩表）；工时永久 |
| 保留 | 事件按月分区，归档策略在 09 运维手册定 |
| 安全 | OIDC + RLS + webhook HMAC；生产环境拒绝 demo 身份与明文凭据 |
| 时区 | 存储 UTC；展示按组织时区（默认 `Asia/Shanghai`） |
| 浏览器 | 最近两个大版本的 Chrome / Safari / Edge；不做 IE |
| 可访问性 | 键盘可达、焦点可见；不做完整 WCAG 认证 |
