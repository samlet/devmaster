# 06 集成契约与事件设计

> 上游：[01](01-方案评估与关键决策.md) ADR-0006/0007、[02](02-需求范围与系统边界.md) §5、
> [04](04-领域模型与数据设计.md) §6。
> 原则：**先冻结契约，再接运行时。** 每条外部契约都要有版本、fixtures、SHA-256 manifest
> 与契约门禁（`make contract-check`）——这是 BK↔FI、engagement↔settlement 验证过的路径。

## 1. 集成面总览

```text
                    ┌───────────────────────┐
   Gitea  ─webhook─►│                       │─outbox─► PPM        （工时 → LABOR 实际成本）
   Gitea  ◄─对账───│      devmaster        │─outbox─► it-solution（版本注册表 / 部署校验）
                    │                       │─HTTP──► approver    （发布审批）
   artifact ◄─引用─│                       │─HTTP──► artifact    （发布说明/报告引用）
                    └───────────────────────┘
```

| 方向 | 对象 | 协议 | 契约 | 里程碑 |
|---|---|---|---|---|
| 入站 | Gitea | HTTP webhook + REST 对账 | §4 | M4 |
| 出站 | PPM | NATS JetStream | §5（C1/C2） | M4/M5 |
| 出站/入站 | it-solution | gRPC 只读 + NATS | §6（C3/C4） | M5 |
| 出站 | approver | HTTP | §7（C5） | M3 |
| 引用 | artifact | gRPC | §8 | M3 |
| 身份 | Keycloak | OIDC | §9（C6） | M0 |

**v1 不接**：BK、FI、wallet、humanres、relink、PLM、it-swarm、QA。理由见 01 ADR-0006 与 02 §5。

## 2. 事件规范

### 2.1 流与主题

```text
Stream:   DEVMASTER_EVENTS        （file storage，7 天保留，max_msgs 按需）
Subjects: dev.v1.{domain}.{entity}.{action}
```

命名规则与 PPM / plant-maint 一致：

| 规则 | 说明 |
|---|---|
| 全小写 | JetStream subject 大小写敏感 |
| 点分隔，从粗到细 | 可 `dev.v1.work.>` 整体订阅 |
| 动作用过去式 | `logged` 而非 `log` |
| 不带实体 ID | ID 放 payload，避免 subject 基数爆炸 |
| 前缀 `dev.v1` | 将来 v2 并行 |

已实测本机 `nats stream ls` 无 `dev.>` 主题，`DEVMASTER_EVENTS` 未被占用。

### 2.2 信封

```json
{
  "event_id": "<UUIDv5，确定性>",
  "event_type": "dev.v1.work.logged",
  "event_version": 1,
  "occurred_at": "2026-10-27T08:00:00Z",
  "organization_id": "<uuid>",
  "aggregate_type": "work_log",
  "aggregate_id": "<uuid>",
  "aggregate_version": 1,
  "producer": "devmaster-server",
  "traceparent": "00-...-...-01",
  "payload": {}
}
```

```text
event_id = UUIDv5(DEVMASTER_NAMESPACE, "{aggregate_type}:{aggregate_id}:{event_type}:{aggregate_version}")
```

确定性 `event_id` 让"同一事实重发"变成幂等操作；消费方按 `event_id` 去重，按
`aggregate_version` 丢弃旧版本。

### 2.3 payload 红线

- 不含姓名、邮箱、头像 URL、IP；人员只放 `sub`（UUID）。
- 不含工作项标题/描述正文（可能含客户名或未公开信息）；只放 `key` 与结构化字段。
- 不含附件字节、不含代码内容。

## 3. 出站事件清单

| # | Subject | 触发 | payload 关键字段 | 消费方 |
|---|---|---|---|---|
| E1 | `dev.v1.workitem.created` | 工作项创建 | `work_item_id, key, product_code, type, reporter_id` | PPM（可选统计） |
| E2 | `dev.v1.workitem.transitioned` | 状态迁移 | `work_item_id, key, from, to, resolution, actor_id, version_id` | PPM / it-swarm（可选） |
| E3 | `dev.v1.workitem.assigned` | 指派变更 | `work_item_id, key, assignee_id, previous_assignee_id` | —（通知用） |
| E4 | `dev.v1.sprint.started` | 冲刺开始 | `sprint_id, board_id, product_code, committed_points, committed_items, start_at, end_at` | PPM（可选） |
| E5 | `dev.v1.sprint.closed` | 冲刺关闭 | `sprint_id, committed_points, added_points, completed_points, carried_over, closed_at` | PPM（可选） |
| E6 | `dev.v1.version.released` | 版本发布 | `version_id, product_code, version, tag, commit_from, commit_to, evidence_ref, released_at` | **it-solution** |
| E7 | `dev.v1.work.logged` | 工时记录 | `work_log_id, work_item_key, product_code, minutes, work_date, project_code, wbs_code, author_id, grade_code, source` | **PPM** |
| E8 | `dev.v1.work.reversed` | 工时更正 | `work_log_id, reversal_of, minutes, project_code, wbs_code, author_id` | **PPM** |
| E9 | `dev.v1.release.submitted` | 提交发布（**内部触发**） | `version_id, release_record_id, product_code, version, submitted_by` | devmaster 自身 consumer → 起 `ReleaseWorkflow` |

E1–E5 中只有 E6/E7/E8 是**硬契约**（有下游行动）；其余先发布、不承诺消费方。
这样做的理由：契约一旦承诺就要维护兼容，先让它们以"通知"身份存在，等真有消费方再升格。

E9 是**自寻址事件**：发布流程不靠"请求里同步起工作流"（写库成功但起流程失败会让用户
卡在 PENDING_APPROVAL 且无法重提），而是写库 + outbox，由自己的 consumer 起流程。
外部系统不消费它，也不在兼容承诺范围内——它的消费者只有 devmaster 自己。

## 4. 入站：Gitea

### 4.1 webhook

```text
POST http://127.0.0.1:8291/integrations/gitea/webhook
Headers:
  X-Gitea-Event: push | pull_request | create
  X-Gitea-Signature: <hmac-sha256(secret, raw_body)>   ← 必须校验，失败 401
  X-Gitea-Delivery: <uuid>                              ← 用于日志关联与去重
```

| 事件 | 处理 |
|---|---|
| `push` | 对每个 commit：解析 message 中的 key → upsert `work_item_commits` |
| `pull_request` | 按 `pr_no` 更新 `pr_state`（opened/closed/merged）与分支 |
| `create`（tag） | 记录 tag → 供发布核对（不直接改版本状态） |

**解析规则**：

```text
正则：\b[A-Z][A-Z0-9]{1,9}-\d+\b
只匹配当前组织内存在的 product key（避免把 "UTF-8" 之类误判）
一个 commit 可关联多个工作项；一个工作项可关联多个 commit
```

**幂等**：`unique (work_item_id, repo, commit_sha)`；重复投递直接忽略（返回 200）。
**不校验分支**：任何分支的提交都算关联，但 `pr_state=MERGED` 才算"已合并"（守卫用）。

### 4.2 每日对账

webhook 会丢、会乱序、会在服务重启时错过。只靠 webhook 的关联率在真实团队里通常 70%–85%。

```text
Temporal Schedule: 每日 02:00（组织时区）
Activity:
  1. 取该组织所有 repo + 上次水位（repo_sync_cursor）
  2. 调 Gitea API: GET /repos/{owner}/{repo}/commits?since={cursor}&per_page=100
  3. 逐页解析、upsert、推进水位
  4. 记录指标 devmaster_gitea_link_rate
```

水位存 `repo_sync_cursors(repo, last_commit_at, last_sha)`；失败保留水位、下次重跑（幂等）。

### 4.3 关联率指标

```text
link_rate = 有至少一个 commit 的工作项数 / (有 merged PR 的工作项数 + 无 PR 但已 DONE 的工作项数)
```

目标 ≥ 99%（M4 验收）。低于 95% 告警——通常意味着 webhook secret 错了或对账任务没跑。

## 5. PPM 契约（C1 / C2）

### 5.1 映射

```text
dev.v1.work.logged
  └─► PPM 消费者（source_system=DEVMASTER）
        ├─ 幂等键：source_system + event_id
        ├─ 定位 WBS：project_code + wbs_code（缺失则挂项目级，标记 UNALLOCATED）
        ├─ 折算金额：minutes / 60 × hourly_rate(grade_code, work_date)
        └─ 写 LABOR 实际成本（category=LABOR, source=DEVMASTER）
```

### 5.2 金额折算与费率

**devmaster 不发金额，只发分钟。** 金额是 PPM 的职责（它是成本控制面），费率也归 PPM。

PPM 侧已新增（C9，**已交付**）：

| 变更 | 内容 |
|---|---|
| 来源标识 | `actual_costs.source_system = DEVMASTER`（PPM 的来源列是文本，不需要枚举迁移；投影按来源分别对账） |
| 费率主数据 | `labor_rates(organization_id, grade_code, currency, valid_from, valid_to, hourly_rate_minor)`，`amount_minor` scale=4（PPM ADR-0004）；管理接口 `CostService.UpsertLaborRate` / `ListLaborRates` |
| 消费者 | 独立流 `DEVMASTER_EVENTS`（`dev.>`）+ durable `dev-worklog-projection`，订阅 `dev.v1.work.logged` / `dev.v1.work.reversed`，投影为 `LABOR` 实际成本 |
| 缺失处理 | 缺 `grade_code` 或缺费率 → 事件 `DEFERRED`（`LABOR_RATE_MISSING`），**不按 0 计**；补齐后由 30 秒重放循环入账 |

**为什么费率在 PPM**：如果 devmaster 自己算钱，它就成了第二个成本口径；而 PPM 已经有
`amount_minor scale=4`、成本类别、期间、结算规则。让 devmaster 只发"多少分钟"，是把
"事实"和"计价"分开——工时是事实，费率是政策，政策会变，事实不会。

**`grade_code` 的来源**：v1 取 Keycloak 用户属性（人工维护），由 `user_profiles` 投影同步；
缺失时工时仍可记录，但 PPM 侧 `HELD` 并告警。humanres 接入后改为从其人员投影取（v2）。
工时记录里的 `grade_code` 是**创建时快照**——职级调整不追溯历史工时，否则成本会随人事变动漂移。

### 5.3 更正

`dev.v1.work.reversed` 发负分钟，PPM 生成一条负向 LABOR 投影（`is_reversal=true`），
与原记录通过 `reversal_of` 关联。**不修改原投影**（与 FI 的红字同纪律）。

### 5.4 契约门禁（C2，已交付）

PPM 仓已落地（对应 PPM `docs/06 §9`）：

```text
contracts/events/envelope.dev.v1.schema.json       入站信封的只读副本
contracts/events/dev.v1.work.logged.schema.json
contracts/events/dev.v1.work.reversed.schema.json
contracts/fixtures/dev.v1.work.logged.json
contracts/fixtures/dev.v1.work.reversed.json
contracts/manifest.json                            含上述文件的 SHA-256
```

`make contract-check` 按事件前缀选信封：`ppm.v1.*` 用 PPM 自己的，`dev.v1.*` 用入站副本。
**devmaster 侧改 payload 字段时，必须先改 PPM 的 schema 与 fixture 再改代码**，
否则门禁会红——这是刻意的：入站契约的兼容性由消费方判定。

链 B 当前是通的（工时 → LABOR 实际成本），验收证据见 PPM `docs/06 §9.8`。

## 6. it-solution 契约（C3 / C4）

### 6.1 CheckVersion（C3）

```proto
service VersionRegistryService {
  rpc CheckVersion(CheckVersionRequest) returns (CheckVersionResponse);
}

message CheckVersionRequest {
  string product_code = 1;   // HOSP
  string version = 2;        // 2.4.1
}

message CheckVersionResponse {
  bool exists = 1;
  bool released = 2;
  string version_id = 3;
  string status = 4;         // PLANNED / IN_PROGRESS / RELEASED / ARCHIVED / CANCELLED
  google.protobuf.Timestamp released_at = 5;
}
```

- 鉴权：`devmaster-service`（client_credentials），scope `version:read`；
- 语义：产品不存在 → `NOT_FOUND`；版本不存在 → `exists=false`（**不报错**，调用方据此决定拒绝/放行）；
- 性能预算：P99 < 50ms；it-solution 侧按 `(product_code, version)` 缓存 60 秒（发布是低频事件）；
- 超时：500ms，1 次重试；
- 降级：it-solution 配 `fail_closed`（生产部署，默认）或 `fail_open_with_flag`（本地走查，部署记录打 `VERSION_UNVERIFIED` 标记）。

**it-solution 的落点**：`RecordDeployment` 前调用；`released=false` 时拒绝并返回
`VERSION_NOT_RELEASED`，提示"先发布或走豁免"。豁免需要 `DEV_ADMIN` 角色 + 原因，落审计。

### 6.2 部署回执（C4，v1 可选）

**裁决（2026-10-27）**：链 A 的"版本 → 客户"报表放在 **it-solution** 侧，不放 devmaster。

理由：部署数据是 it-solution 的事实，devmaster 再存一份就是缓存，缓存就有漂移；
而"哪些客户在跑 2.4.0"本来就是 it-solution 的领域问题。devmaster 只回答
"这个 BUG 影响哪些版本"（`affects_version_id`），两个查询在界面上拼起来即可。

因此 C4 降级为**可选**：it-solution 若愿意发部署事件，devmaster 可用于"版本健康度"看板；
v1 不做，避免多一条要维护的契约。

### 6.3 版本发布与部署的时序

```text
devmaster: ReleaseRecord → PUBLISHED（tag 已打、证据已存）
   └─ dev.v1.version.released
        └─ it-solution: 收到后刷新版本缓存（可选）
             └─ 部署时 CheckVersion → released=true → 允许落位
```

**顺序不能反**：先发布再部署。若客户现场必须先部署后补发布（紧急修复），走豁免 + 审计，
不允许静默绕过。

## 7. approver 契约（C5）

### 7.1 流程定义

```text
processKey: devmaster-release-approval
businessKey: <version_id>            ← 幂等键，同一版本重复提交复用同一实例
表单字段:
  product_code, version, tag, commit_from, commit_to,
  item_count, release_notes_ref, submitted_by
用户任务: 单人审批（角色 RELEASE_APPROVER）
```

### 7.2 调用与等待

```text
SubmitRelease（devmaster 写库 + outbox）
  └─ relay → dev.v1.release.submitted（自寻址事件）
       └─ consumer → Temporal: ReleaseWorkflow(version_id)
            ├─ Activity CheckSubmittable（版本仍是 PENDING_APPROVAL 才起流程）
            ├─ Activity StartApproval → approver HTTP
            ├─ Activity PollApproval（每 10s，最长 24h）
            │     ├─ COMPLETED + APPROVED → 继续
            │     └─ REJECTED / 超时 → ReleaseRecord=FAILED + 通知
            ├─ Activity CreateTag（Gitea API，幂等：tag 已存在视为成功）
            ├─ Activity SealEvidence（artifact，发布说明 + 提交范围）
            └─ 写 ReleaseRecord=PUBLISHED + version=RELEASED + outbox E6
```

**为什么轮询而不是回调**：approver 目前没有通用出站回调 connector（it-solution 的经验）。
轮询间隔 10 秒、上限 24 小时，对发布这种低频动作完全够用；等 approver 有了回调再换，
换的时候只改 Activity，不动领域模型。

### 7.3 四眼

审批人不能是 `submitted_by`。devmaster 提交时把 `submitted_by` 写进表单变量，
approver 侧用现有的人员校验拒绝自审批；devmaster 侧在 `PollApproval` 拿到
`approver_id` 后再校验一次（双保险，且能给出明确错误）。

## 8. artifact 契约

| 用途 | content type | 引用方式 |
|---|---|---|
| 发布说明 | `devmaster.release-notes` | `versions.notes_ref = content_id:revision_id`（固定版本） |
| 测试报告 | `devmaster.test-report` | `release_records.evidence_ref` |
| 缺陷附件 | 复用 artifact 现有类型 | `attachments(content_id, revision_id)` |

规则与 it-solution 一致：**只存固定版本引用，不存预签名 URL**；下载时重新申请短期 URL；
devmaster 不代理字节。

### 8.1 已落地的存证路径

artifact 侧 registry 用 `devmaster` profile 登记（`go run ./cmd/registry-seed -profile devmaster -tenant <tid>`），
两个类型都只接受内联证据，不开放对象上传：

| 项 | 值 |
|---|---|
| 资源类型 | `INLINE_TEXT`（≤ 64 KiB） |
| 资源角色 | `evidence` |
| 敏感级 | `INTERNAL` |
| 命名空间 | `devmaster` |
| 认证 | Keycloak client `content-worker`，client_credentials，角色 `content.service`，claim `tenant_id` / `org_ids` |

调用序列（`internal/platform/artifact`，由 `SealEvidence` 活动驱动）：

```text
CreateContent(content_type=devmaster.test-report, metadata={release_id, version_id, ...})
  → CreateResource(revision_id, role=evidence, kind=INLINE_TEXT, inline_text=<证据 Markdown>)
  → SealRevision(revision_id, expected_version)
  → ListRevisionResources(revision_id)   ← 回读并比对 SHA-256
  → evidence_ref = content_id:revision_id
```

幂等：幂等键 = `devmaster-evidence-{content,resource}-<指纹>`，指纹是
（content_type + title + metadata + role + 载荷 SHA-256）的 SHA-256 前 20 字节。
同一份证据重试回放同一修订；载荷或元数据变化即另一份证据。

证据文本刻意不含时间戳（否则重放会算出新指纹、堆出重复内容）。时间以 artifact 的
`revision.created_at` 为准。

验收：`make test-evidence`（首封新建 / 重放命中同一修订 / 载荷变化落新修订）。

## 9. 身份契约（C6）

| 项 | 值 |
|---|---|
| realm | `devmaster` |
| client `devmaster-web` | Authorization Code + PKCE，`http://127.0.0.1:3031/api/auth/callback` |
| client `devmaster-service` | client_credentials，scope `version:read`、`integration:write` |
| 角色 | `DEV_VIEWER` / `DEV_MEMBER` / `DEV_LEAD` / `RELEASE_APPROVER` / `DEV_ADMIN` |
| 组织声明 | `org_ids`（数组），与 artifact 同约定；缺失则拒绝 |

`devmaster-service` 只能调集成 RPC（`CheckVersion`、`IngestGitea`），不能调业务写接口（03 §7.3）。

### 9.1 通知收件人解析（subject-registry）

通知的 `recipient_id` 遵循 `kind:id` 约定，只有 `user:` 需要主体目录：

| kind | 形态 | 解析来源 |
|---|---|---|
| 个人 | `user:<anchor_id>` | subject-registry `Resolve("keycloak", sub)` |
| 角色 | `role:RELEASE_APPROVER` | 固定常量（催办降级目标） |
| 团队 | `team:devmaster` | notify 配置的默认收件人 |

解析规则：

```text
发布成功/失败：recipientFor(SubmittedBy)
  ├─ 命中 → user:<anchor_id>
  └─ 未命中/未接入/目录故障 → 留空 → notify 落到 team:devmaster
催办：role:RELEASE_APPROVER（审批完成前拿不到审批人 id，不猜）
```

`user:` 用 anchor_id 而不是 Keycloak `sub`：换 IdP 后 anchor 不变，notify 侧的
频控计数、退订记录、收件箱历史不会集体失效。

主体目录不可用不阻断通知（旁路），因此生产不强制 `subject_registry.enabled`——
与 `artifact.enabled` 不同，后者是审计事实，缺了发布链就少一环。

## 10. 失败恢复矩阵

| 场景 | 表现 | 处理 | 是否丢事实 |
|---|---|---|---|
| Gitea webhook 重复 | 同 commit 多次投递 | 唯一索引忽略，返回 200 | 否 |
| Gitea webhook 丢失 | 关联缺失 | 每日对账补齐 | 否（延迟 ≤ 24h） |
| Gitea 不可达 | 对账失败 | 保留水位，下次重跑 | 否 |
| NATS 不可达 | outbox 积压 | relay 退避重试；业务写入不受影响 | 否 |
| consumer 停机 | 事件堆积 | JetStream 保留 7 天，恢复后继续 | 否（7 天内） |
| PPM 不可达 | E7 积压 | outbox 重试；工时照常记录 | 否 |
| PPM 缺费率 | 投影 HELD | 预警列表；补费率后重放 | 否（挂起非丢弃） |
| approver 不可达 | 发布停在 PENDING_APPROVAL | 工作流重试；可人工重提 | 否 |
| 审批超时 24h | 发布失败 | ReleaseRecord=FAILED + 通知；可新建尝试 | 否 |
| it-solution 校验超时 | 部署被拒或放行 | 按 `fail_closed` / `fail_open_with_flag` | 视策略 |
| devmaster 不可达 | it-solution 部署阻塞 | 同上；恢复后自动放行 | 否 |
| 事件重复投递 | 消费方重复处理 | `event_id` 去重 | 否 |
| 事件乱序 | 旧状态覆盖新状态 | 按 `aggregate_version` 丢弃旧版本 | 否 |

**没有"丢事实"的格子**，这是设计目标：所有失败都停在"可重放"的位置，而不是"少了一条"。

## 11. 契约门禁

```bash
make contract-check
  ├─ 校验 contracts/events/*.json 与 fixtures 的 JSON Schema 一致
  ├─ 校验 manifest.json 的 SHA-256（fixtures 被改动但没更新 manifest → 失败）
  ├─ buf breaking 对比 main（proto 不兼容变更 → 失败）
  └─ 扫描 payload 红线（姓名/邮箱/标题字段名 → 失败）
```

`contracts/` 结构：

```text
contracts/
  events/    dev.v1.work.logged.v1.json  dev.v1.version.released.v1.json ...
  fixtures/  *.golden.json
  manifest.json
```
