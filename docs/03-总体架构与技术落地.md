# 03 总体架构与技术落地

> 上游：[01](01-方案评估与关键决策.md) D1～D4、[02](02-需求范围与系统边界.md)。
> 本文只写"怎么跑起来"：进程、请求链路、事务边界、读模型、安全、运维。
> 表结构与状态机见 [04](04-领域模型与数据设计.md)，契约见 [06](06-集成契约与事件设计.md)。

## 1. 一句话架构

> **Next.js(App Router) → BFF(Route Handler + 签名) → gRPC → Go 模块化单体**
> **Temporal 管时间与人工等待**，**PostgreSQL 是执行事实的真相源**，
> **NATS JetStream 承载跨系统事实**，**Atlas 管迁移**，**Keycloak 管身份**。

与 PPM / it-solution 保持完全一致的技术形态，不引入新范式。本地开发只用 Homebrew 原生服务。

## 2. 进程与职责

| 进程 | 职责 | 监听 | 是否随 `make dev` |
|---|---|---|---|
| `server` | gRPC 业务接口 + HTTP 网关（healthz / metrics / Gitea webhook） | `:50091` / `:8291` | ✅ |
| `relay` | outbox → JetStream，至少一次投递 | 无 | ✅ |
| `consumer` | 入站事件 → Inbox → 投影；自寻址事件 → 起工作流（发布） | 无 | ✅ |
| `worker` | Temporal worker：发布、冲刺时钟、缺陷计时、Gitea 对账 | 无 | ✅ |
| `web` | Next.js App Router + BFF | `:3031` | ❌（单独 `make web-dev`） |
| `migrate` | Atlas 迁移执行器（一次性） | 无 | ❌ |

**进程数刻意控制在 5 个**（不含 web 与一次性 migrate），与 PPM 对齐。不再拆"搜索服务""报表服务"——
那会把单库 JOIN 变成跨服务调用，是净损失。

## 3. 请求链路

```text
浏览器
  │  HTTPS / 同源
  ▼
Next.js Route Handler（BFF）
  │  1. 从加密 HttpOnly Cookie 取会话，解出 access token
  │  2. 加签名头：X-Devmaster-Bff: <HMAC(secret, ts + path + body_sha256)>
  │  3. Connect-ES 调 gRPC
  ▼
gRPC 拦截器链
  │  ① OIDC 验签（issuer / audience / exp，JWKS 缓存）
  │  ② 组织注入（从 token 的 org 声明取，拒绝前端传入）
  │  ③ 方法级授权（方法 → 所需角色的静态矩阵，未登记方法一律拒绝）
  │  ④ 幂等键提取（写方法必填）
  ▼
应用服务（internal/<module>/application）
  │  事务开始
  │   ├─ 领域校验（状态机、守卫、不变量）
  │   ├─ 写业务表
  │   ├─ 写 work_item_events（需要时）
  │   ├─ 写 outbox_events
  │   └─ 写 idempotency_keys（响应快照）
  │  事务提交
  ▼
PostgreSQL
```

**BFF 不做业务判断**，只做会话、签名、错误翻译。所有授权在 Go 侧，浏览器永远不持有 access token。

### 3.1 错误模型

```text
gRPC status + ErrorDetail
{
  "code": "WORKITEM_INVALID_TRANSITION",
  "message": "BUG 不能从 OPEN 直接到 CLOSED",
  "retryable": false,
  "field_violations": [{"field": "status", "reason": "..."}],
  "trace_id": "..."
}
```

约定：

- `INVALID_ARGUMENT`：字段校验失败（带 `field_violations`，前端逐字段标红）；
- `FAILED_PRECONDITION`：状态机/守卫拒绝（带当前状态与允许动作）；
- `ABORTED`：幂等键冲突（同 key 异 payload）或并发 CAS 失败；
- `NOT_FOUND`：跨组织/跨产品越权一律返回 `NOT_FOUND`，不泄露存在性；
- `UNAVAILABLE`：依赖不可达（Temporal / Gitea），`retryable=true`。

## 4. 事务与一致性

### 4.1 一个写 RPC = 一个 PG 事务

业务表、事件、outbox、幂等记录必须同事务。这是生态的既有纪律（BK 的 outbox、FI 的凭证），
不发明新的。

**跨聚合写也在同一事务**：关闭 sprint 要同时写 `sprints`、`sprint_scope_events`、
若干 `work_items.sprint_id`、`outbox_events`——同库，天然原子。**不拆成"先关 sprint 再回流"两步**，
否则中途失败会留下"已关闭但工作项还挂着"的脏状态。

### 4.2 外部调用不在事务内

| 调用 | 位置 | 失败处理 |
|---|---|---|
| approver 起流程 | 提交后由 outbox 事件触发 Temporal，再由 Activity 调 approver | 事件可重放；`CheckSubmittable` 防重复起流程 |
| Gitea 打 tag | `ReleaseWorkflow` 的 Activity | 幂等（tag 已存在视为成功）；失败重试后人工介入 |
| 发通知 | 由 outbox 事件驱动，失败不阻断业务 | 与 PPM 同：通知不是业务事实 |

### 4.3 事件投递语义

- **出站**：at-least-once。`event_id` 用 UUIDv5 确定性派生，消费方按 `event_id` 去重。
- **入站**：at-least-once + Inbox 去重（`(source, event_id)` 唯一）。
- **不承诺**跨系统 exactly-once，也不承诺顺序（消费方按 `aggregate_version` 丢弃旧版本）。

### 4.4 一致性对账

| 对账 | 频率 | 断言 |
|---|---|---|
| 当前态 vs 事件折叠 | 每日 | `work_items.status == fold(events)`，不一致告警 |
| outbox 积压 | 每分钟（metric） | 超过 1000 条或最老超过 5 分钟告警 |
| Gitea 关联 | 每日 | 关联率 = 有 commit 的工作项 /（有 merged PR 的工作项 + 无 PR 但已 DONE 的工作项），定义见 [06 §4.3](06-集成契约与事件设计.md) |
| 版本 scope | 发布时 | `RELEASED` 后 `version_id` 不可变（触发器） |

## 5. 读模型与查询

**不做 CQRS 双库**。所有读走同一 PG，靠索引与少量物化表。

| 读场景 | 实现 | 索引 |
|---|---|---|
| 看板（单 sprint） | `work_items WHERE sprint_id=? ORDER BY rank` | `(sprint_id, rank)` |
| Backlog | `WHERE product_id=? AND sprint_id IS NULL AND status NOT IN (终态) ORDER BY rank` | `(product_id, sprint_id, rank)` |
| 我的待办 | `WHERE assignee_id=? AND status NOT IN (...)` | `(assignee_id, status)` |
| 版本 scope | `WHERE version_id=?` | `(version_id)` |
| 全文检索 | `search_vector @@ websearch_to_tsquery(...)` + 结构化过滤 | GIN |
| 燃尽 | `sprint_daily_snapshot`（每日由 worker 写） | `(sprint_id, snapshot_date)` |
| 报表（M6） | 读 `work_item_events` + 快照，按周/月聚合 | `(occurred_at)` + 分区裁剪 |

**燃尽为什么不实时算**：一个 3 周的 sprint 有几千条事件，每次打开页面扫一遍是浪费；
每日快照 + 当天的增量事件足够。快照由 Temporal Schedule 触发，失败可重跑（幂等 upsert）。

**搜索的中文处理**：优先 `pg_jieba`（若本机 PG 已装），否则用二元切分（`bigram`）+
`simple` 配置。**不引 ES**（01 ADR-0009）。搜索结果按 `updated_at` 倒序，不做相关性调权。

## 6. 幂等与并发

### 6.1 幂等键

```text
idempotency_keys(
  key text primary key,
  method text,              -- /dev.v1.WorkItemService/Transition
  request_hash bytea,       -- SHA-256(canonical request)
  response_hash bytea,      -- 成功响应的哈希（用于重放比对）
  response_blob jsonb,      -- 成功响应快照（重放直接返回）
  created_at, expires_at    -- 保留 7 天
)
```

- 同 key 同 payload → 返回原响应（`replayed=true`）；
- 同 key 异 payload → `ABORTED`（与 BK 的幂等语义一致）；
- 过期清理由 worker 每日执行。

### 6.2 并发控制

| 场景 | 手段 |
|---|---|
| 工作项编辑 | CAS：`UPDATE ... WHERE id=? AND version=?`，失败返回 `ABORTED` + 当前版本 |
| 拖拽排序 | 单事务内改 `rank` + `status`，CAS 校验版本 |
| 冲刺开始/关闭 | `SELECT ... FOR UPDATE` 锁 sprint 行 |
| 版本发布 | 锁 version 行 + 唯一索引兜底（一个版本同时只有一个进行中的 ReleaseRecord） |
| 编号生成 | `UPDATE product_counters SET next_seq=next_seq+1 RETURNING next_seq`（行锁） |

## 7. 身份、授权与安全

### 7.1 Keycloak

| 项 | 值 |
|---|---|
| realm | `devmaster`（独立，不与其他仓共用） |
| client `devmaster-web` | Authorization Code + PKCE，redirect `http://127.0.0.1:3031/api/auth/callback` |
| client `devmaster-service` | client_credentials，用于 importer / 集成调用 |
| 角色 | `DEV_VIEWER` / `DEV_MEMBER` / `DEV_LEAD` / `RELEASE_APPROVER` / `DEV_ADMIN` |
| 组织声明 | token 中的 `org_ids`（与 artifact 同约定） |

### 7.2 BFF 签名

`X-Devmaster-Bff: v1:<ts>:<hmac_sha256(secret, ts + "\n" + method + "\n" + path + "\n" + body_sha256)>`

- 时间窗 ±60 秒，超出拒绝（防重放）；
- secret 只从环境变量读，生产拒绝默认值；
- Go 侧对**所有**非 health/metrics 请求校验，webhook 例外（走 Gitea 自己的签名）。

### 7.3 授权矩阵

| 方法 | 所需角色 |
|---|---|
| `ProductService.*`（读） | `DEV_VIEWER` |
| `ProductService.Create/Update`、成员管理、字段注册表 | `DEV_ADMIN` |
| `WorkItemService.Create/Update/Comment/LogWork` | `DEV_MEMBER`（且是产品成员） |
| `WorkItemService.Transition`（关闭他人） | `DEV_LEAD` |
| `SprintService.Start/Close/ChangeScope` | `DEV_LEAD` |
| `VersionService.Create/Update` | `DEV_LEAD` |
| `VersionService.SubmitRelease` | `DEV_LEAD` |
| `IntegrationService.CheckVersion` | `devmaster-service`（服务身份） |
| 未登记方法 | 一律拒绝 |

### 7.4 数据库与 webhook

- 运行时角色 `devmaster_app`：非 owner、非 superuser；RLS `FORCE ROW LEVEL SECURITY`；
- `relay` / `consumer` 用独立 `BYPASSRLS` 角色，只授 `outbox_events` / `inbox_events` 所需列；
- Gitea webhook 校验 `X-Gitea-Signature`（HMAC-SHA256，secret 每环境独立）；
- 生产环境（`DEVMASTER_ENV=production`）启动即拒绝：demo 身份、默认 secret、无 TLS 的 BFF 回调。

### 7.5 用户资料投影

事件与业务表只存 `sub`。界面要显示姓名/头像，所以有一张本地投影：

```text
user_profiles(sub text primary key, display_name, email, avatar_url, updated_at)
```

由 worker 每日从 Keycloak Admin API 增量刷新（按 `sub` 列表批量查）。**这是缓存，不是主数据**；
查不到时界面显示 `sub` 前 8 位，不阻塞任何操作。humanres 接入后改为从其投影取（v2）。

## 8. 可观测性

### 8.1 日志

JSON 结构化，每条必带：`trace_id`、`organization_id`、`method`、`duration_ms`、`result`。
有工作项上下文时带 `work_item_key`（不带标题，避免日志里出现业务内容）。

### 8.2 指标

```text
devmaster_grpc_request_duration_seconds{method,code}
devmaster_workitem_transition_total{type,from,to}
devmaster_outbox_pending
devmaster_outbox_oldest_age_seconds
devmaster_inbox_dead_letter_total
devmaster_sprint_active{board}
devmaster_gitea_link_rate
devmaster_event_fold_mismatch_total
```

最后三个是**业务指标**，比技术指标更重要：关联率掉了说明 webhook/对账坏了，
折叠不一致说明事件日志失真，这两件事不会以 ERROR 形式出现。

### 8.3 健康检查

`/healthz` 分组件：`postgres` / `nats_jetstream` / `temporal` / `keycloak`，任一失败返回 503 + `trace_id`。
`/metrics` 只绑 `127.0.0.1`（生产由 Prometheus 侧拉）。

## 9. 部署与本地启动

### 9.1 本地（开发/走查）

```bash
brew services start postgresql@18
brew services start nats-server
temporal server start-dev --db-filename ~/.temporal/devmaster.db   # 必须带持久化
# Gitea 已在 :3123 运行（brew services）

make db-create        # 建 devmaster_owner / devmaster_app 与 devmaster_dev / devmaster_test
make migrate
make seed             # 演示组织 + 3 个产品 + 一个 sprint + 20 个工作项
make dev              # server + relay + consumer + worker
make web-dev          # :3031
```

**Temporal 必须带 `--db-filename`**（与 PPM 同一个坑）：默认内存持久化，重启后 schedule 与
工作流历史全清空，而四个进程都还活着、日志里没有 ERROR。

### 9.2 走查数据包

`assets/datasets/<name>/` 下用 CSV + `manifest.json` + `expectations.json`，与 PPM / it-solution 同格式：

```text
00-master/   products.csv components.csv members.csv
01-work/     work_items.csv links.csv comments.csv
02-sprint/   sprints.csv scope_events.csv
03-version/  versions.csv releases.csv
04-worklog/  work_logs.csv
expectations.json
```

导入器 `cmd/importer` 支持 `--reset` 整包重建、`--dry-run` 结构校验；重跑幂等（按业务键查后建）。

### 9.3 生产形态（后续）

v1 只承诺单机部署：五个进程 + PG + NATS + Temporal + Keycloak，由 systemd/launchd 托管。
**不做** K8s、不做多活、不做读写分离。备份策略与 PPM 同（手工 `pg_dump` + 定期演练），
上线前补齐自动化备份与告警（09 运维手册）。

## 10. 容量与压测

| 项 | 目标 | 验证方式 |
|---|---|---|
| 10 万工作项 + 100 万事件 | 看板 P95 < 300ms | `perfbaseline` 灌数据后跑固定查询集 |
| 全文检索 | P95 < 500ms | 同上，20 组查询 |
| 写峰值 10 rps | 无锁等待超时 | 并发脚本：20 个写者 × 5 分钟 |
| outbox 积压恢复 | 10 万条 5 分钟内清空 | 停 relay 灌数据后恢复 |

压测工具与 PPM 的 `perfbaseline` 同思路：确定性数据 + 固定查询集 + 记录 P50/P95/P99 到文档。

## 11. 技术选型理由

| 选择 | 理由 | 代价 |
|---|---|---|
| 模块化单体 | 工作项、冲刺、版本、工时大量同库 JOIN 与同事务原子性；单人维护 | 将来只能按模块拆，不能按"服务"拆 |
| 不做 CQRS 双库 | 读场景简单（看板/列表/搜索），物化一张燃尽快照就够 | 报表复杂后可能要数据集市 |
| 不做完整 Event Sourcing | 当前态查询是主路径，重放重建成本高 | 事件与当前态要靠对账保证一致 |
| PG 全文检索 | 十万级足够，少一个进程 | 相关性排序弱，中文分词依赖扩展 |
| LexoRank | 拖拽只写一行 | 字符串变长，需要低频 rebalance |
| Temporal | 发布审批、冲刺时钟、缺陷计时、对账都是"等时间/等人" | 多一个依赖，本地要带持久化启动 |
| NATS JetStream | 与生态一致，流与 subject 已规划 | 不保证顺序，消费方要按版本号丢弃旧事件 |

## 12. 未来拆分点（只记录，不实施）

| 候选 | 触发条件 | 拆法 |
|---|---|---|
| `reporting` | 报表查询拖慢在线看板（P95 > 1s） | 独立只读库 + 事件订阅，主库不参与聚合 |
| `search` | 需要代码级/跨仓搜索 | 交给 Gitea，或引入独立索引，devmaster 只存 ID |
| `integration` | 对接系统超过 8 个 | 独立网关进程，领域层完全不感知外部契约 |

**没有触发条件就不拆**。这条与 BK 的 `deployment-evaluation`、PPM 的 ADR 同一条纪律。
