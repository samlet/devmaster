> 本文档是 02～09 的裁决依据；与本文冲突的后续文档以本文为准。

## 0. 结论

1. **方向成立，但立项目的不是"缺一个 Jira"。** 生态已有 123 个 git 仓（`apps/` 85 + `portals/` 38）、
   二十多个可运行服务，却没有一处记录"谁在改什么、为什么改、改完进了哪个版本、哪个客户在跑这个版本"。
   缺的是**研发执行的事实源**，不是又一块看板。
2. **定位：devmaster 是研发执行域（execution of record），不是项目管理，不是成本账。**
   项目结构与预算在 PPM，账在 FI，部署在 it-solution，生产事件在 it-swarm。
   devmaster 只拥有四类事实：**工作项、冲刺、版本、工时**。
3. **价值只有三条链能证明**（§2 D1）：缺陷→版本→部署→客户、工时→项目成本→毛利、版本→审批→证据→验收。
   三条链任一不通，这个项目就退化成"自建了一个更差的 Jira"，应当直接停，改用 Gitea Issues。
4. **FinOps 不新开项目，也不扩 fi 内核。** 归集与优化落 it-swarm（其路线图 D07 已列"成本治理"），
   用量由 cloud-pivot 与云账单提供，fi 只增加"分摊结果"一个事实词汇（§2 D4）。
5. **最大风险是 ROI，不是技术。** 技术形态与 PPM / it-solution 完全一致，没有新范式；
   真正的风险是做完之后没人用、或用了但不产生可核算的事实。守卫写在 §9。

## 1. draft 的六个缺口

| # | 缺口 | 现状 | 后果 |
|---|---|---|---|
| G1 | 没有定位 | 只说"参考 Jira 的任务/缺陷/冲刺/版本迭代" | 这四件套是商品化能力，单做没有理由自建；必须回答"为什么不是 Jira" |
| G2 | 没有事实边界 | 列了 8 个相关项目，没说谁拥有哪个事实 | 与 PPM 的项目、it-solution 的部署、it-swarm 的 Incident、PLM 的 Release 四处重叠 |
| G3 | 没有控制强度 | 没说复刻 Jira 的哪一层 | Jira 的复杂度 80% 来自多团队配置隔离（workflow scheme / field config / permission scheme），照抄等于自找维护地狱 |
| G4 | 集成面失控 | 8 个项目全部"相关" | 每接一个系统要处理契约版本、幂等、重放、权限、组织映射、失败恢复六件事 |
| G5 | 没有验收口径 | 没说"什么算做完" | 生态惯例是"真实 gRPC + 真实 PG + race + 走查数据包"才算交付，缺这条会退化成 demo |
| G6 | 两个域捆在一起 | FinOps（云财务运营）与研发管理写在同一个 draft | FinOps 的事实源是资源与用量，不是工作项；捆在一起会失焦，且两边都做不深 |

## 2. 四个决策

### D1 业务定位 —— ✅ 已确认（2026-10-27）：软件研发执行事实源，服务三条链

**决策**：v1 只做**软件研发**的生产管理（工作项、缺陷、冲刺、版本、工时），服务三条可追溯链；
**不做**美术/音频资产生产跟踪（那需要与 DCC / Perforce / ShotGrid 集成，是另一个产品），
**不做**软件测试用例与执行管理（v2 再议，见 §10 O4）。

**三条链（这是本项目唯一的立项理由）**：

```text
链 A 影响面   BUG ─affects_version─► Version ─(product,version)─► it-solution 部署 ─► 客户
链 B 投入产出 WorkLog ─dev.v1.work.logged─► PPM(LABOR 实际) ─► FI ─► 项目毛利
链 C 交付合规 Version ─ReleaseRecord(approver 审批 + artifact 证据)─► 部署 / 验收
```

- **链 A** 是 Jira + ERP 都做不到开箱即用的：缺陷修在 2.4.1，哪些客户还在 2.4.0？
  这需要版本注册表（devmaster）+ 部署台账（it-solution）联查。对游戏运营同样成立：
  一个客户端崩溃修在 build 1234，哪些区服还在跑 1233。
- **链 B** 是参考文档里 Room 8 Group 的做法（Jira 工时回传 ERP 算收入与进度）。
  本生态的落点是 PPM 的 LABOR 实际成本，再由 PPM 结算进 FI。
- **链 C** 把"发布"从一次口头决定变成有审批、有证据、有部署回执的事实。

**理由**：生态里 PPM 管"花多少钱、值不值"，it-solution 管"交付给谁、验收没有"，
it-swarm 管"线上出了什么事"。唯独中间那层"东西是怎么被做出来的"是空的。
这一层如果不用系统记录，上面三层全部靠人填，数据可信度归零。

**代价**：v1 的用户是研发团队，不是管理层。管理层要的报表（人效、交付预测）在 M6 才有，
前五个里程碑看不到"给老板看的东西"。这个代价必须付，否则会为了报表提前做聚合层，
而聚合层在没有干净事实之前一定是错的。

### D2 事实边界 —— ✅ 已确认（2026-10-27）：devmaster 拥有执行事实，不拥有项目、账、部署、生产事件

| 事实 | 权威源 | devmaster 的角色 |
|---|---|---|
| 工作项、状态迁移、评论、链接 | **devmaster** | 拥有 |
| 冲刺、范围变更、承诺快照 | **devmaster** | 拥有 |
| 产品版本（软件）、发布记录、发布说明 | **devmaster** | 拥有 |
| 研发工时（worklog） | **devmaster** | 拥有（见 O1） |
| 代码、分支、提交、PR、tag | Gitea | 消费 webhook + 定期对账 |
| 项目结构、WBS、预算、EVM | PPM | **弱引用** `project_code` / `wbs_code`，不建项目表 |
| 部署记录、客户验收、订阅 | it-solution | 推送 `version.released`，消费部署回执（只读对账） |
| 生产事件、问题、变更、CMDB | it-swarm | 只做引用（缺陷来源 / 修复关联），不复制状态机 |
| 产品工程 Release（Rev A/B、BOM、ECO） | PLM | **不同义，不互相同步**（见 ADR-0005） |
| 凭证、总账、成本 | FI | 不直连；成本经 PPM 归集后由 PPM 结算 |
| 审批过程与意见 | approver | 发起流程，消费结果 |
| 合同、验收单、测试报告、发布说明附件 | artifact | 只存 `content_id:revision_id` |
| 人员与组织 | Keycloak（v1）/ humanres（后续投影） | 只存 `sub`，不存姓名 |

**这条边界的含义**：devmaster 里没有"项目"这张表。工作项上的 `project_code` 是可空字符串，
对不上时只打 `PROJECT_REF_UNRESOLVED` 标记，不阻断任何操作。理由与 PPM 对 engagement 的裁决同源：
两个系统各自建一套项目主数据，最终一定漂移，而漂移的项目编码会让成本归集变成猜谜。

### D3 控制强度 —— ✅ 已确认（2026-10-27）：固定状态机 + 类型化字段，不做 Jira 式配置器

**决策**：
- 状态机按工作项类型**固定**，写在代码里（`workflow.go` 的迁移表），数据库只存实例状态；
- 字段扩展走 `custom_fields JSONB` + `field_registry`（每产品注册字段名/类型/是否必填），
  应用层按注册表校验，DB 只做 GIN 索引；
- 可配的只有"守卫开关"：是否必须关联版本才能关闭缺陷、是否必须 code review 才能进 `IN_REVIEW`、
  发布是否必须走 approver。开关有默认值，且默认值必须可用；
- **不做**图形化流程设计器、不做 permission scheme、不做 field configuration scheme。

**理由**：Jira 的复杂度不是功能多，是**多团队共用一套实例**逼出来的配置隔离层。
本生态的产品线由同一批人维护，配置隔离的收益接近于零，成本却是永久的：
每加一个配置维度，查询、报表、迁移、测试的组合数就翻一倍。
PPM 的 ADR 也做过同样裁决（Status Profile 简化为固定状态机），这里是同一条纪律的延续。

**代价**：如果将来真的出现"外包团队要用完全不同的流程"，只能加类型（`type` 枚举）而不是加配置。
这是可接受的：类型是代码，可以 review、可以测试；配置是数据，出问题只能靠用户描述。

### D4 FinOps 归属 —— ✅ 已确认（2026-10-27）：it-swarm 承接，fi 只加一个词汇，不新开项目

先把问题拆开，四件事常被混为一谈：

| 层 | 问题 | 事实源 |
|---|---|---|
| 用量 | 谁用了多少 ECS / OSS / RDS / 带宽 | cloud-pivot、云厂商账单 |
| 归集 | 这笔钱属于哪个游戏 / 区服 / 活动 / 环境 | 标签 + 分摊规则 |
| 账务 | 记到哪个成本中心 / 项目，是否内部结算 | FI |
| 优化 | 闲置、规格过大、预留实例覆盖率 | 运营域 |

**四条路的取舍**：

| 方案 | 能复用 | 代价 | 判断 |
|---|---|---|---|
| 扩 fi 成 FinOps | 科目、成本中心、费用分摊、期间 | fi 变成 ETL + 计费 + 优化引擎，破坏"事实入站→规则→凭证"的纯净；fi 是**每节点一个账房**，云成本是**平台级**口径，放节点账套里天然错位；fi 已 80 期，改动风险高 | ❌ 不扩成 FinOps，只加一个"分摊结果"词汇 |
| 新开 finops 项目 | 域干净 | 重复建模资源、标签、归属；多一个域要接 cloud-pivot + fi + it-swarm 三个系统 | ❌ 不推荐 |
| 扩 it-swarm | CMDB（资源-服务-区服拓扑）、行业包（游戏）、路线图 D07 已列"成本治理" | it-swarm 自身还在 M1a | ✅ **推荐** |
| 扩 cloud-pivot | 资源元数据、租户归属、用量 | 它是供给控制面，不是成本域；覆盖不了第三方云与非 SaaS 资源 | ⚠️ 只做数据源 |

**建议的分工**：

```text
云厂商账单/成本管家 ──► it-swarm（账单行 + 标签治理 + 分摊规则 + 闲置识别 + 预算告警）
cloud-pivot        ──► it-swarm（资源元数据、租户/项目归属、生命周期事件）
                          │
                          └── cost.allocation@v1（已确定的分摊结果）──► fi（成本中心/项目维度）
```

- **先 showback，后 chargeback**：v1 只出"谁花了多少"的报表，不生成内部结算凭证。
  chargeback 涉及内部交易定价与税务，等 fi 的内部交易台账能力就绪（M65 已有）再单独立项。
- **行业维度不进 fi 内核**：游戏/区服/活动用"成本中心树 + 标签映射表"表达，
  不给 fi 加游戏专有字段。fi 的维度模型是通用的，一旦为某个行业开洞，后面每个行业都会要一个洞。
- **FinOps 与 devmaster 无事实交集**。唯一的接触点是研发环境（dev/test 集群）的成本，
  那是 it-swarm 按 `env` 标签归集的一行，不需要 devmaster 参与。

**结论**：draft 里"扩 fi 还是单开项目"这个二选一本身是伪命题——正确的落点是第三个系统。
如果 FinOps 的优先级高于 devmaster，就先做 it-swarm 的成本治理阶段，而不是先做 devmaster。

## 3. 关键取舍（ADR）

### ADR-0001 devmaster 是研发执行事实源，不是第二套项目管理

**决策**：不建 `project` 表；工作项上的 `project_code` / `wbs_code` 是**可空弱引用**，不做外键、不做同步。

**理由**：PPM 已有项目、WBS、预算、EVM；engagement 的 `Project` 已被裁决为"独立结点，无耦合"。
再建一套项目，就是 PPM 文档里警告的"第四套项目"。弱引用的代价是"对不上时不知道找谁"，
用 `PROJECT_REF_UNRESOLVED` 标记 + 看板提示解决，比双向同步便宜一个数量级。

**代价**：跨系统报表（按项目看研发投入）需要 join 两个库，只能走 PPM 的读接口或数据集市，不能一条 SQL。

### ADR-0002 事件日志 + 当前态投影，不做完整 Event Sourcing

**决策**：`work_item_events` append-only 记录每一次状态迁移、字段关键变更、范围变更；
`work_items` 表保存当前态（同事务更新）。燃尽、周期时间、累积流图全部由事件派生。

**理由**：完整 Event Sourcing 要重放重建，查询成本高、迁移复杂；而"事件日志 + 当前态"能同时满足
审计（谁在什么时候改了什么）与查询（看板一次查询出结果）。这与 BK 的 outbox + ledger、
FI 的不可变凭证是同一种纪律，不是新范式。

**代价**：两张表要保证一致，必须同事务写，且要有对账任务（`event_replay_check`）验证
"当前态 == 事件折叠结果"，否则事件日志会悄悄失真。

### ADR-0003 冲刺是"承诺快照"，不是"容器"

**决策**：`sprint_scope_events` 记录 `COMMITTED / ADDED / REMOVED / COMPLETED / REOPENED` 五类事实，
每次带当时的点数。燃尽图与"范围蔓延率"（`added_after_start / committed`）都从这张表算。

**理由**：Jira 的燃尽图经常失真，因为 sprint 的成员可以被事后增删，历史没有留痕。
把"范围变更"变成一等事实后，燃尽图不再需要"猜"，也顺带得到了一个更有用的指标：
**这个团队是被插单拖垮的，还是估算不准**。

**代价**：规划 sprint 时要显式提交"承诺"（一次批量操作），比 Jira 的"拖进去就算"多一步。
这一步是刻意的：没有承诺，就没有范围蔓延可言。

### ADR-0004 工时只增不改

**决策**：`work_logs` 不允许 UPDATE / DELETE。更正走**反向记录**（`reversal_of` 指向原记录，分钟取负），
两条记录都保留。`minutes` 用整数分钟，不用小数小时。

**理由**：工时是链 B 的源头，一旦可改，成本追溯就断链——"上个月这个项目为什么多花了 8 万"
永远回答不了。整数分钟避免浮点累加误差（PPM 的金额纪律是同一条思路：整数最小单位）。

**代价**：用户填错要两步（作废 + 重填），前端要提供"更正"而不是"编辑"。

### ADR-0005 `Version` 是交付物身份，与 PLM 的 `Release` 不同义

**决策**：devmaster 的实体叫 `Version`（如 `hospitality 2.4.0`），发布动作叫 `ReleaseRecord`
（审批 + tag + commit range + 证据）。PLM 的 `Release` 是**产品工程发布快照**（Rev A/B，面向制造），
两者不合并、不互相同步。

**理由**：PLM 的 Release 回答"这个产品在工程上是什么"（BOM、规格、ECO），
devmaster 的 Version 回答"这版软件包含哪些改动、部署到哪"。强行统一会让 PLM 的
不可变快照语义被软件版本的频繁小版本稀释。

**代价**：同一个产品在两个系统里各有一个"版本"概念，需要在 it-solution 的部署记录处显式对齐
（部署的是**软件版本**，不是工程版本）。这条要在 02 文档的术语表里写清楚。

### ADR-0006 v1 集成面限定为五个对象

**决策**：

| 方向 | 对象 | 内容 |
|---|---|---|
| 入站 | Gitea | webhook（push / pull_request / tag）+ 定期对账扫描 |
| 出站 | PPM | `dev.v1.work.logged`（LABOR 实际成本） |
| 出站 | it-solution | `dev.v1.version.released`（版本注册表） |
| 出站 | approver / artifact | 发布审批、发布证据 |

BK、FI、wallet、humanres、relink 在 v1 **不做运行时对接**：BK 与研发无关；
FI 的成本入口必须唯一（经 PPM），否则会出现两个成本来源；wallet 无关；
humanres 的人员投影等 Keycloak 不够用时再接；relink 的客户反馈先用手填 `external_ref`。

**理由**：每接一个系统要处理契约版本、幂等、重放、权限、组织映射、失败恢复六件事。
五个对象已经是一个季度的量。契约先冻结，运行时后接，是 BK↔FI 验证过的路径。

**代价**：v1 的"客户反馈驱动研发"是断的（要人工贴单号）。可接受，因为这条链的商业价值
远低于链 A/B/C。

### ADR-0007 版本注册表是 it-solution 部署的前置校验

**决策**：it-solution 的 `Deployment.version` 必须在 devmaster 的版本注册表中存在且状态为
`RELEASED`（或显式豁免）。devmaster 提供只读查询 `CheckVersion`，it-solution 在部署落位时调用。

**理由**：这是链 A 的锚点。没有这个校验，"客户在跑哪个版本"就永远是脏数据，
影响面分析也就无从谈起。校验放在 it-solution 侧（调用方），devmaster 不反向写部署记录，
保持"谁的事实谁写"。

**代价**：it-solution 要多一次同步调用，且 devmaster 不可用时部署会阻塞。
降级策略：`fail_closed`（默认，生产部署）或 `fail_open_with_flag`（本地走查），由 it-solution 配置。

### ADR-0008 身份用 Keycloak 独立 realm，组织隔离用 RLS

**决策**：realm `devmaster`，不与其他仓共用（artifact 的 realm 修复经验表明共用 realm 会让
角色作用域互相污染）。`devmaster-web` 走 Authorization Code + PKCE，`devmaster-service` 走
client_credentials。数据库 RLS `FORCE ROW LEVEL SECURITY`，运行时角色非 owner、非 superuser。

**理由**：与 PPM / it-swarm 完全一致，没有新决策，只是执行纪律。

### ADR-0009 搜索用 PostgreSQL，不引 Elasticsearch

**决策**：`tsvector` + GIN 全文索引 + 结构化过滤（product / type / status / assignee / version）。

**理由**：十万级工作项、百万级事件，PG 的全文检索足够；引入 ES 意味着多一个进程、
一套同步机制、一份运维负担。等真的出现"跨 123 个仓的代码级搜索"需求，那是 Gitea 的职责，
不是 devmaster 的。

### ADR-0010 排序用 LexoRank 字符串

**决策**：backlog 与看板列内排序用 LexoRank（字符串，字典序可比较），插入时取相邻两项中点。

**理由**：整数 rank 在中间插入要重排后续所有行，一次拖拽可能写几百行并触发大量事件；
LexoRank 一次只写一行。代价是字符串会变长，需要定期 rebalance（低频、可后台做）。

## 4. 与 Jira 的对齐与偏离

**先回答"为什么不买 Jira"**。三个现实约束，按权重排序：

1. **集成深度**：Jira 的工时与版本事实要进 PPM/FI，必须自建中间件（Room 8 Group 的案例就是
   专门做了 Jira→D365 的回传）。中间件的成本不低于自建一个轻量执行域，且多了一层要维护的同步。
2. **数据驻留**：本生态全部部署在自有机房/本机，SaaS 版不可选；Data Center 版的许可与运维
   在百人规模是一笔持续支出。
3. **模型贴合**：Jira 没有"版本→部署→客户"的对象，也没有"工时→项目成本"的语义，
   这两条链在 Jira 里只能靠插件和自定义字段拼，拼出来的东西无法保证口径。

**但这不构成"照抄 Jira"的理由**。下面这张表说明哪些抄、哪些不抄：

| Jira 能力 | 本方案 | 理由 |
|---|---|---|
| Issue Type / 字段 | 保留，但字段类型固定 + `custom_fields` 注册表 | 不做 field configuration scheme（D3） |
| Workflow（可配置） | 固定状态机 + 类型差异 + 守卫开关 | D3 |
| Board / Backlog / Rank | 保留，LexoRank | ADR-0010 |
| Sprint / Burndown | 保留，但范围变更是一等事实 | ADR-0003 |
| Version / Release | 保留，拆成 `Version` + `ReleaseRecord` | ADR-0005 |
| Component / Label | 保留 Component（树），Label 用 `tags text[]` | 简化 |
| Worklog | 保留，只增不改，进成本链 | ADR-0004 |
| JQL（查询语言） | **不做**，用结构化过滤器 + 保存的视图 | JQL 是半个产品，收益低于成本 |
| Automation（规则引擎） | **不做**，用 Temporal 工作流替代固定几类自动化 | 规则引擎的调试成本极高 |
| Marketplace / 插件 | **不做** | 单人维护，插件生态是负资产 |
| Permission Scheme | **不做**，用角色 + 产品成员关系 | D3 |
| 跨项目链接 | 保留 `WorkItemLink`，不做跨实例 | 单实例部署 |
| 测试管理（Zephyr 类） | **v1 不做** | 见 O4 |
| 服务台 / 客户 SLA | **不做**，那是 it-swarm 的 Incident；缺陷的修复时限是内部计时器（M3），不是客户 SLA | D2 |

### 4.1 为什么不是直接用 Gitea Issues

| 需求 | Gitea Issues | devmaster |
|---|---|---|
| 任务 / 缺陷 / 标签 / 里程碑 | ✅ 原生 | ✅ |
| 冲刺、范围变更、燃尽 | ❌ 只有 milestone，无 timebox | ✅ ADR-0003 |
| 工时 → 项目成本 | ❌ | ✅ 链 B |
| 版本 → 部署 → 客户影响面 | ❌ | ✅ 链 A |
| 发布审批与证据 | ❌ | ✅ 链 C |
| 与代码提交/PR 关联 | ✅ 原生 | webhook + 每日对账 |

**结论**：只需要前两行，用 Gitea Issues；需要后三行，才有 devmaster。这也是为什么 §8 的验收
把"三条链端到端断言"写成不可协商项——它们是这个项目与 Gitea Issues 的全部差别。

## 5. 领域模型草案

### 5.1 实体关系

```text
Product
 ├── Component（树，可选层级）
 ├── Board ── Sprint（时间盒；同时最多一个 ACTIVE）
 ├── Version ── ReleaseRecord（审批实例 / tag / commit range / 证据引用）
 └── WorkItem
      ├── sprint_id           ──► Sprint
      ├── version_id          ──► Version（fix version）
      ├── affects_version_id  ──► Version（缺陷影响面，链 A 的起点）
      ├── WorkItemLink（BLOCKS / RELATES / DUPLICATES / CAUSES）
      ├── Comment
      ├── Attachment（artifact content_id:revision_id）
      ├── WorkLog（分钟；成本事实，只增不改）
      └── WorkItemEvent（append-only，状态迁移与关键变更）
```

`Product` 不是"项目"，是**被开发的软件**（hospitality / healthcare / fi / ppm …）。
一个 Product 有稳定的 key（`HOSP`），工作项编号 `HOSP-1234` 由该 key + 序列生成。

### 5.2 状态机（固定，按类型）

| 类型 | 状态迁移 | 终态 |
|---|---|---|
| `EPIC` | `OPEN → IN_PROGRESS → DONE`（+ `CANCELLED`） | DONE / CANCELLED |
| `STORY` / `TASK` | `BACKLOG → TODO → IN_PROGRESS → IN_REVIEW → DONE`（+ `CANCELLED`） | DONE / CANCELLED |
| `BUG` | `OPEN → IN_PROGRESS → RESOLVED → VERIFIED → CLOSED`（+ `REOPENED` / `WONTFIX`） | CLOSED / WONTFIX |
| `SUBTASK` | 跟随父项，不独立进 sprint | 同父项 |

`BLOCKED` **不是状态**，是 flag（`blocked_reason`），因为"阻塞"与"进行中"可以同时成立——
把它做成状态是 Jira 里最常见的建模错误之一。

`resolution` 枚举：`FIXED / WONTFIX / DUPLICATE / CANNOT_REPRODUCE / BY_DESIGN / OBSOLETE`。
关闭必须带 resolution（守卫，可配）。

### 5.3 核心不变量（草案）

> 完整清单（I1–I9）与强制手段以 [04 §4](04-领域模型与数据设计.md) 为准，这里只列决定模型形状的五条。

| # | 不变量 | 强制手段 |
|---|---|---|
| I1 | 一个 Board 同时最多一个 `ACTIVE` sprint | 部分唯一索引 `(board_id) WHERE state='ACTIVE'` |
| I2 | 一个工作项同时只属于一个 sprint；跨 sprint 移动必须成对写 `REMOVED` + `ADDED` | `sprint_id` 单列 + 领域层成对写事件（集成测试断言事件成对） |
| I3 | 状态迁移必须走迁移表，每次迁移写事件 + outbox（同事务） | 领域层唯一入口 `Transition()`，静态检查禁止直接改 status |
| I4 | `RELEASED` 版本的 scope 冻结，只能开新版本 | 触发器拒绝 `version_id` 变更 |
| I5 | `work_logs` 不可 UPDATE/DELETE | 数据库权限（只授 INSERT/SELECT）+ 反向记录 |

### 5.4 表结构要点

```sql
-- 工作项（当前态）
work_items(
  id uuid pk, organization_id uuid, key text,           -- HOSP-1234
  product_id uuid, component_id uuid null, type text, status text, resolution text null,
  title text, description_md text,
  priority smallint, severity text null,                 -- 仅 BUG
  reporter_id uuid, assignee_id uuid null,
  sprint_id uuid null, version_id uuid null, affects_version_id uuid null,
  parent_id uuid null, story_points int null,
  estimate_minutes int null, remaining_minutes int null,
  rank text, project_code text null, wbs_code text null,
  external_ref text null,                                -- it-solution 工单 / it-swarm Incident
  custom_fields jsonb not null default '{}',
  blocked_reason text null, version int not null default 0,   -- CAS
  created_at, updated_at, resolved_at, closed_at,
  unique (organization_id, key)
)

-- 事件（append-only，按月分区）
work_item_events(id bigserial, organization_id, work_item_id, event_type,
  from_status, to_status, actor_id, payload jsonb, occurred_at)

-- 冲刺与范围
sprints(id, board_id, name, goal, state, start_at, end_at, capacity_points, committed_points, closed_at)
sprint_scope_events(sprint_id, work_item_id, action, points_at_event, occurred_at, actor_id)

-- 版本与发布
versions(id, product_id, name, status, planned_date, released_at, milestone_label, notes_ref)
release_records(id, version_id, tag, commit_from, commit_to, approval_instance_id,
  evidence_ref, released_by, released_at, status)

-- 工时
work_logs(id, organization_id, work_item_id, author_id, minutes int, work_date,
  note, project_code, wbs_code, source, reversal_of uuid null, created_at)
```

### 5.5 与外部系统的引用关系

```text
work_items.project_code ──弱引用──► PPM project.code      （不校验、不阻断）
work_items.wbs_code     ──弱引用──► PPM wbs.code
versions.(product,name) ◄──校验──── it-solution deployments.version
work_items.external_ref ──弱引用──► it-solution ServiceTicket / it-swarm Incident
attachments.ref         ──强引用──► artifact content_id:revision_id（固定版本）
release_records.approval_instance_id ──强引用──► approver 实例 ID
```

## 6. 集成契约

> 原则与 PPM 一致：**先冻结契约，再接运行时。** 每条外部契约要有版本、fixtures、
> SHA-256 manifest 与契约门禁（`make contract-check`）。

### 6.1 事件规范（出站）

```text
Stream:   DEVMASTER_EVENTS      （file storage，7 天保留）
Subjects: dev.v1.{domain}.{entity}.{action}
```

已实测：本机 `nats stream ls` 无 `dev.>` 主题，`DEVMASTER_EVENTS` 未被占用。
信封与 PPM 完全一致（`event_id` 用 UUIDv5 确定性派生），消费方可安全去重。

### 6.2 事件清单

| Subject | 触发 | payload 关键字段 |
|---|---|---|
| `dev.v1.workitem.created` | 工作项创建 | `work_item_id, key, product_id, type, reporter_id` |
| `dev.v1.workitem.transitioned` | 状态迁移 | `work_item_id, key, from, to, actor_id, resolution` |
| `dev.v1.workitem.assigned` | 指派变更 | `work_item_id, assignee_id, previous_assignee_id` |
| `dev.v1.sprint.started` | 冲刺开始（承诺冻结） | `sprint_id, board_id, committed_points, committed_items` |
| `dev.v1.sprint.closed` | 冲刺关闭 | `sprint_id, committed_points, added_points, completed_points, carried_over` |
| `dev.v1.version.released` | 版本发布 | `version_id, product_code, version, tag, commit_from, commit_to, evidence_ref` |
| `dev.v1.work.logged` | 工时记录 | `work_log_id, work_item_key, minutes, work_date, project_code, wbs_code, author_id` |
| `dev.v1.work.reversed` | 工时更正 | `work_log_id, reversal_of, minutes` |

**payload 红线**：不含姓名、邮箱、头像 URL；人员只放 `sub`。不含代码内容、不含附件字节。

另有**自寻址事件** `dev.v1.release.submitted`（只给自身 consumer 起发布工作流，外部不承诺消费），
不计入外部契约。详见 [06 §3](06-集成契约与事件设计.md)。

### 6.3 入站：Gitea

```text
Gitea（org webhook）──► POST :8291/integrations/gitea/webhook
  events: push / pull_request / create(tag)
  HMAC-SHA256 校验（X-Gitea-Signature）
  → 解析 commit message 中的工作项 key（正则 \b[A-Z][A-Z0-9]{1,9}-\d+\b）
  → work_item_commits(work_item_id, repo, branch, commit_sha, pr_no, pr_state)
```

**不信任 webhook 的完整性**：Temporal 每日对账任务按 `repo + since` 拉 Gitea API，
补齐丢失的提交。理由：webhook 会丢、会乱序、会因服务重启错过；只靠 webhook 的关联率
在真实团队里通常只有 70%～85%，而对账能拉到 99%。

### 6.4 跨仓依赖（需单独立项，不是 devmaster 单方面能改的）

| # | 对端 | 变更 | 阻塞 |
|---|---|---|---|
| C1 | PPM | 成本来源枚举增加 `DEVMASTER`；新增 `dev.v1.work.logged` 消费者，投影为 `LABOR` 实际成本 | ✅ **已交付**（PPM `0011` + consumer，见 PPM docs/06 §9） |
| C2 | PPM | 契约文档 06 新增 C9 条目 + fixtures + manifest | ✅ **已交付**（PPM C9） |
| C3 | it-solution | `Deployment` 落位前调用 `CheckVersion`（只读）；`fail_open_with_flag` 可配 | 链 A；M5 |
| C4 | it-solution | 链 A 的"版本→客户"报表在 it-solution 侧实现（部署数据是它的事实）；部署回执事件降为可选，v1 不做 | 链 A 的报表 |
| C5 | approver | 新增流程定义 `devmaster-release-approval`（表单 + 单人审批） | 链 C；M3 |
| C6 | Keycloak | 新 realm `devmaster` + 两个 client + 角色 | M0 |
| C7 | Gitea | org 级 webhook + 只读 API token（repo scope） | M4 |

C1 是本项目最关键的跨仓依赖，**已于 2026-10-27 在 PPM 侧落地**（`0011` 迁移 + 工时消费者 +
费率 RPC + 契约门禁，见 PPM `docs/06 §9`）。链 B 因此不再是纸面设计：
工时只发分钟，PPM 按 `labor_rates` 折算成 `LABOR` 实际成本，缺费率时暂存而非按 0 计。

### 6.5 明确不做的集成

| 不做 | 理由 |
|---|---|
| devmaster → FI 直连 | 成本入口必须唯一（PPM 结算），否则 FI 出现两个来源 |
| devmaster ↔ it-swarm 双向同步 | Incident 与 BUG 生命周期不同，只做引用 |
| devmaster ↔ PLM 版本同步 | ADR-0005，两个 Version 不同义 |
| Jira 导入（v1） | 无历史数据；将来用 CSV 适配器，走数据包通道（见 O2） |
| CI/CD 执行 | devmaster 只记录版本与提交范围，不编排构建 |

### 7.4 工程纪律（与生态逐条对齐）

| 纪律 | 落地 | 检查 |
|---|---|---|
| Schema 只走版本化迁移 | Atlas `migrate-diff`，服务不 AutoMigrate | CI 比对 ent schema 与 migrations |
| 写操作带幂等键 | 所有写 RPC 必填，落 `idempotency_keys` | 同 key 重放同结果，异 payload 冲突 |
| 并发用乐观锁 | `version` + `expected_version` | 并发测试：两个写者只有一个成功 |
| 事件只经 outbox | 业务事务内写 `outbox_events` | 静态检查禁止直接 Publish |
| 事件无敏感信息 | 只放 ID / 编码 / 点数 / 分钟 | 契约门禁扫描 |
| 组织隔离 | RLS + 应用层谓词 | 跨组织越权返回 NotFound |
| 契约先行 | proto 唯一源，Go/TS 双生成入库 | `buf lint` + `buf breaking` |
| 真实依赖验收 | 真 PG / 真 JetStream / 真 Temporal / 真 Gitea / 真 Keycloak | `make test-integration` 不允许 mock 声称通过 |
| 长流程进 Temporal | 不用 goroutine 定时器、不用 cron 扫库 | 代码审查 |

### 7.5 性能与容量

| 量级 | 判断 |
|---|---|
| 10 万工作项 / 100 万事件 | PG 单库足够；`work_item_events` 按月分区（预留，先不建） |
| 单 sprint 看板（数百项） | 一次索引查询，不缓存 |
| 燃尽 | 由 `sprint_daily_snapshot`（Temporal 每日快照）供数，不每次扫事件表 |
| 全文检索 | `tsvector` GIN，中文用 `simple` 配置 + `pg_jieba`（若可用）否则二元切分 |
| 写入峰值 | 单团队每天数百次迁移，无压力；真正的写放大来自 rank 重排（ADR-0010 已解） |
